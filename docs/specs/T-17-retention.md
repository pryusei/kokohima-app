# T-17 仕様書：古いデータの掃除と保持期間

- 状態：下書き
- タスク票：docs/tasks/T-17-retention.md
- 関係する要件：要求定義書「AI時代の攻撃を前提にした運用」（保存するデータを減らす）、NF-08。issue pryusei/kokohima-app#38 の残り

## 概要
終わった誘い・募集・成立した予定（相手・時刻・エリア・ひとこと）は、今は無期限に残っている。これを、予定の時間の終わりから30日で、毎分の掃除で消す。期限の過ぎた招待リンクと、過去のくり返しの例外も消す。あわせて、表ごとの保持期間を1つの表にまとめる。また、どの端末からもログインしていない人（有効なセッションがない人）の連携では、カレンダーの定期の確認を止める。

## 決めたこと（利用者の回答）
1. 終わった誘い・募集・成立した予定は、終わってから30日で消す。
2. 連携したまま有効なセッションがない人の、カレンダーの定期の確認は止める（次にログインしたら再開）。
3. 成立数の集計（NF-08）のための記録は、今は残さない。過去の成立を後から数えられなくなることを受け入れる（#46 で集計を作るときに決める）。

変更なし（毎分の掃除と、定期の確認の割り当ての変更だけ）。

### 2. 終わった誘い・募集・予定
- 毎分の掃除で、次の行を消す。状態では絞らない（時間の終わりを過ぎていれば、どの状態でも終わっている）。
  - 誘い：`ends_at < ?cutoff AND (counter_ends_at IS NULL OR counter_ends_at < ?cutoff)`。`?cutoff` は今から30日前。代わりの時間で成立した予定は、代わりの時間で作られるので、その終わりまで待つ。
  - 募集：`ends_at < ?cutoff`。
- 予定（`meetups`）・参加者（`meetup_participants`）・宛先（`broadcast_recipients`）・.ics の鍵（`ics_tokens`）・リンクの参照（`link_preview_refs`）は、外部キーの CASCADE で一緒に消える。予定は誘い・募集と同じ時間なので、予定だけ先に消えることも、予定だけ残ることもない。
- 両方の参加者の履歴から同時に消える（片方だけ残さない）。相手あてのお知らせ（90日）が、消えた誘い・予定を指すことがある。開くと、今の「見つかりませんでした」になる（「確認事項」）。
- 1回に消すのは、誘い・募集それぞれ1000行まで（`CLEANUP_BATCH`）。消す行は `ends_at` のインデックスで選ぶ（`DELETE ... WHERE id IN (SELECT id ... ORDER BY ends_at LIMIT ?)`）。
- リンクのプレビューの結果の行は、参照がなくなるので、T-08 の掃除で消える。

### 3. 招待リンク
- 期限 `expires_at` が今から30日より前の行を消す（使い切ったもの・無効化したものも、期限で消える。期限は最長7日。T-02）。1回に1000行まで。

### 4. くり返しの例外
- `local_date` が、UTC の日付で今日の2日前より前の行を消す。タイムゾーンの差は最大1日なので、どのタイムゾーンでも過去の日付になっている。1回に1000行まで。
- ルールを消すと、例外は CASCADE で消える（今のまま）。

### 5. 休眠中の連携の定期の確認
- 定期の確認の割り当て（`connectionsDueForSync`。T-06・T-12 データの増加）の条件に、「その利用者に有効なセッション（`revoked_at IS NULL AND expires_at > now`）がある」を足す。セッションは最長90日（T-01）。
- 止まるもの：Google の埋まりの取得と、それによるここ暇の自動の取り消し（T-06）と、そこからの自動の「今回は難しい」。止まっている間は、カレンダーで埋まった時間のここ暇が、友達にそのまま見えることがある（受け入れる。本人がログインしていないので、すでに古い情報である）。
- 止まらないもの：成立した予定の書き込み（`activeConnectionsOf`）と、連携の行・トークン（消さない）。
- ログインし直すと、次の割り当て（15分ごと）で確認が戻る。

### 6. 掃除の書き方
- `apps/api/src/jobs/dispatch.ts` の `cleanupExpired` に足す。ほかの掃除と同じく `runStep` で1つずつ独立させる（T-12 データの増加）。step の名前は `cleanup_invitations`・`cleanup_broadcasts`・`cleanup_invite_links`・`cleanup_recurrence_exceptions`。
- SQL は各コンテキストの infra に置く（invitation：誘い・募集、social：招待リンク、availability：例外）。
- 上限で打ち切ったときのログは、T-12 データの増加の書き方に合わせる（件数だけ。ID は出さない）。

## 認可と秘匿
- 閲覧者IDの使い方：API がないので、閲覧者はいない。掃除はすべての利用者の行を、時刻だけで選ぶ。
- 他人のデータに届かないことの保証：消すのは時刻の条件に当たる行だけ。両方の参加者の履歴から同時に消えるので、片方だけに残って相手を推測させることはない。
- 区別させない応答：変わらない（消えた誘い・予定は、ほかの見つからないものと同じ404）。
- ログ：件数と step の名前だけ。

## テスト計画

### 単体テスト（実装PRで必須）
- [ ] 誘い：時間の終わりからちょうど30日の行は残り、それより前の行は消える。代わりの時間があれば、その終わりで判定する。状態によらない
- [ ] 誘い・募集を消すと、予定・参加者・宛先・.ics の鍵・リンクの参照も消え、両方の参加者の一覧・詳細から見えなくなる（404）
- [ ] 30日以内の誘い・募集と、まだ終わっていないものは消えない
- [ ] 招待リンク：期限から30日の境界
- [ ] くり返しの例外：UTC の日付で2日前の境界。ルールは残る
- [ ] 上限：1回で1000行まで消し、残りは次の実行で消える
- [ ] インデックス：4つの掃除の SQL が、表全体を読まない（EXPLAIN QUERY PLAN。`apps/api/src/jobs/dispatch.test.ts` の既存の確かめ方）
- [ ] 独立：1つの掃除が例外を投げても、残りの掃除が走る
- [ ] 休眠中の連携：有効なセッションがない人（すべて失効・期限切れ）は割り当てられない。ログインし直すと割り当てられる。成立した予定の書き込みは止まらない。割り当ての SQL はインデックスを使う
