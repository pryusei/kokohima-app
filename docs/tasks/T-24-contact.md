# T-24 問い合わせのフォーム

## 目的
ログインしている利用者が、設定から運営に不具合・ご意見・個人情報の開示や削除の請求を送れるようにする。送った内容は、運営者だけが入る Slack の非公開のチャンネルに届き、運営者は登録のメールアドレスに返事をする。

## 関係する要件
- 要求定義書「機能要件」：F-22 問い合わせ（実装PRで足す）
- 要求定義書「AI時代の攻撃を前提にした運用」（保存するデータを減らす）：内容は D1 の outbox の行にだけ置き、届けたら消す。Queue のメッセージには受付番号だけを載せる
- 要求定義書「悪用対策と運用」：1人直近24時間で3件まで
- T-19（プライバシー ポリシーの「3.」8 問い合わせに答える、「8.」保存する期間、「9.」本文とアプリをそろえ続ける、「12.」開示・削除の求め）。ログインできない人は今までどおり `ops@kokohima.app`
- 関連：T-01（メールアドレス）、T-10（冪等キー・回数の上限）、T-11・T-20（画面）、T-12（リリースの秘密情報）、T-13（監視・退避キュー）、T-16（退会）、T-17（保持期間）、T-18（画面のエラーの経路の一覧）、T-21（WebKit の E2E）

## スコープ
- やること：
  - 受け口 `POST /api/v1/contact-messages`（ログインした人だけ。本文の上限は冪等キーの処理より前。outbox に1行書くだけ。1人直近24時間に3件まで。内容は1000文字まで）
  - dispatch でこの型の Queue のメッセージを受付番号だけにし、consumer が D1 の行を読んで Slack の Incoming Webhook に送る（利用者の文を `plain_text` に入れ、`&`・`<`・`>` をエスケープし、メンション・リンクを起こさせない。宛先を `new URL()` で確かめ、転送に従わない）。返信先のメールアドレスは送る時に identity から読む
  - 届けたら outbox の内容を消す。退会した人の問い合わせは届けない。送信と重なった退会はアラートで気づく
  - 設定のトップの「このアプリについて」に「問い合わせ」を足し、`/settings/contact` の画面（種類のチップ、内容と文字数、静かな成功と失敗）を作る。部品 `textareaClass`・`CharCount` を `apps/web/src/ui/form.tsx` に足す
  - 公開の日（`packages/shared/src/contactStart.json`）：プライバシー ポリシーの改定日（効力が生じる日）より前は、入口を出さず、API は知らない経路と同じ404。デプロイの検査で改定日と同じことを確かめる。T-19 の改定（#146）と時期を合わせ、1回の予告で両方を知らせてよい
  - 秘密情報 `CONTACT_SLACK_WEBHOOK_URL`（`wrangler secret` だけ）と、E2E の偽の Slack
  - Slack の保持（無料のプランの保持の設定で90日。`retention.ts` の `PLATFORM_RETENTION.contactSlackDays`）
  - 同じ実装PRで、プライバシー ポリシー（集める情報・目的・委託先 Slack・外国の事業者・保存期間・開示の求め。T-19 の改定の手順で7日前に予告）・`retention.ts`・手順書・要求定義書・スキル・T-10/T-11/T-12/T-13/T-16/T-17/T-18/T-21・デザインの資料を直す（仕様書の「実装PRで直すもの」）
- やらないこと（スコープ外）：
  - ログインしていない人のフォーム、自動の返信メール、送った問い合わせの一覧、画面からの返事
  - ファイルの添付、D1 への保存・集計、Slack 以外の届け先、Slack のメッセージを API で消す仕組み
  - 全体の回数の上限、今のひとことの入力欄の見直し

## 受け入れ条件
- [ ] ログインした人が、設定 → 「問い合わせ」で種類を選んで内容を書いて送ると、「送りました」が静かに出て、`#kokohima-contact` に1通届く
- [ ] 届いた文に、種類・内容・返信先（送り主の登録のメールアドレス）・利用者 ID・受け付けた時刻・受付番号が入り、内容の `<!channel>`・`<@...>`・`<URL|文字>` などがメンション・リンクにならず、リンクの展開も起きない。長い内容は `section`（最大2つ）に分かれ、文字の途中で切れない
- [ ] 送り主はいつもアクセストークンの本人で、本文で偽れない。ログインしていない・退会した人は送れない
- [ ] 1人直近24時間に4件目は送れず（429 と `Retry-After`）、静かな文言が出る。内容は1〜1000文字、本文は8KiB まで。8KiB を超える本文は、冪等キーの記録を作らずに400になる
- [ ] 同じ `Idempotency-Key` の再送で、2通届かない
- [ ] 公開の日より前は、設定に「問い合わせ」の行が出ず、API は知らない経路と同じ404 を返す。公開の日（日本時間の0時）から使える。デプロイの日が公開の日より前なら、改定日の行の日付が公開の日と違うとデプロイの検査が止まる
- [ ] outbox の payload にメールアドレスが入らず、Queue のメッセージ（再試行・退避キュー）に内容・利用者 ID・メールアドレスが入らない。届けたら D1 の種類と内容が消える。届かなければ再試行され、最後は退避キューに入って `job_dead_lettered` で気づける
- [ ] webhook の URL が `https://hooks.slack.com/services/...` の形でなければ送らず、転送（3xx）にも従わない
- [ ] 送る前に退会していたら届かない。送信と重なって退会したら `contact_delivered_after_withdrawal`（受付番号だけ）が出る
- [ ] ログ・例外のメッセージに、内容・メールアドレス・利用者 ID・webhook の URL が出ない
- [ ] 送れなかったとき（429・5xx・通信できない・400・409・422）、赤やエラー色を使わずに文言が出て、入力が残る。オフラインでは押せない。PC の配置では左のナビの「設定」が今の画面になる
- [ ] プライバシー ポリシーと `retention.ts`（`contactSlackDays`）が、この実装PRで直っていて、改定日と予告の行が T-19 の改定の手順のとおりに出る
- [ ] 手順書・要求定義書・スキル・T-10/T-11/T-12/T-13/T-16/T-17/T-18/T-21・デザインの資料が、仕様書の「実装PRで直すもの」のとおり直っている
- [ ] 他人のIDでは取得・更新できないテストがある（本文に別の利用者の ID を入れても、送り主は本人のまま。E2E の確かめる経路も本人の送信だけを返す）
- [ ] 単体テストが追加され、通る
- [ ] 仕様書でE2Eの対象にした流れのE2Eテストが通る（Chromium・`mobile`・WebKit の `@iphone`）
- [ ] 仕様書とコードに齟齬がない（仕様の変更は仕様書に反映済み）
- [ ] typecheck・lint・関係するテストが通る
