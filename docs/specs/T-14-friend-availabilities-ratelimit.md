# T-14 仕様書：「みんな」の空きの回数の上限と、残るリスクの見直しの記録

- 状態：合意済み（仕様書PRマージ）
- タスク票：docs/tasks/T-14-friend-availabilities-ratelimit.md
- 関係する要件：要求定義書「サービス拒否」、NF-09。docs/specs/T-10-idempotency-cache-ratelimit.md「回数の上限を付ける経路」、docs/specs/T-08-link-preview.md「名前解決の検査」

## 概要
- `GET /api/v1/friend-availabilities`（「みんな」）は、呼ばれるたびに、見てよい友達全員の手動の枠とくり返しのルールを読み、最長14日分を展開してから500件ずつのページに分ける。友達が多いほど重い。いまは回数の上限がないので、1人の利用者が連打すると D1 の読み取りと CPU 時間を使い続けられる。
- この経路に、利用者IDごとの回数の上限を付ける。仕組みは T-10 の `free_slots` と同じ（`RL_USER`）。
- セキュリティの見直し（2026-11-21）で、あと2件が挙がった。どちらも既存の仕様書で意図して対策しないと決めたもので、見直したうえで変えない。判断と理由を「決定事項」に残す。

## API
既存の経路に、回数の上限を足すだけ。入力・出力の形は変えない。

| メソッド | パス | 認証 | 入力（Zodスキーマ名） | 出力 | 主なエラー |
| --- | --- | --- | --- | --- | --- |
| GET | `/api/v1/friend-availabilities` | Bearer | query：`from`、`to`（最長14日）、`cursor`（変更なし） | 200（変更なし） | 400、401、429 `rate_limited`（この仕様書で足す） |

- 429 は T-10 と同じ Problem Details の形で、`Retry-After: 60` を付ける。どの上限かは返さない。

## データ
変更なし。マイグレーションなし。wrangler の設定（`ratelimits`）も変えない（既存の `RL_USER` を使う）。

## 振る舞い

### 回数の上限（T-10「回数の上限を付ける経路」に1行足す）
| 経路 | まとまりの名前 | キー | 上限 | 仕組み | 超えたとき |
| --- | --- | --- | --- | --- | --- |
| `GET /api/v1/friend-availabilities` | `friend_availabilities` | 利用者 ID | 60秒に20回（拠点ごと、おおよそ） | `RL_USER` | 429 `rate_limited` |

- 数える単位は1回の呼び出し。ページの続き（`cursor` つき）も1回と数える。
  - 「みんな」の画面は、開くたびに続きを最後まで読む。1ページは500件なので、ふつうは1回で終わる。
  - ふつうの使い方（画面を開く、タブに戻る）では届かない値。20回は `free_slots` と同じで、`RL_USER` の設定をそのまま使う。
- 上限は認証の後にかける（`requireAuth` の後）。未認証の呼び出しは、いままでどおり401で、回数に数えない。
- 回数は `friend_availabilities:<利用者ID>` のキーで数える。ほかのまとまり（`free_slots` など）や、ほかの利用者の回数とは別。
- ログは T-10 と同じ。超えたら `{ event: "rate_limited", group: "friend_availabilities" }` だけを出し、利用者 ID は出さない（docs/specs/T-13-monitoring.md の `rate_limited` のアラートの対象になる）。

### 画面（「みんな」）
- 429 を受けたら取り直さない（取り直すと、さらに上限を使う）。カレンダーの候補（T-10）と同じ扱い。
- 前に読めた内容があれば、そのまま出し続ける。読み込みの失敗の文言は出さない。
- 前に読めた内容がなければ、「少し時間をおいて、もう一度開いてください」を静かに出す（`role="status"`、エラー色を使わない）。
- 429 以外の失敗の扱いは変えない。

## 決定事項

1. **`friend-availabilities` に `RL_USER` を使う**：新しい Rate Limiting のバインディングを足さない。上限の値が `free_slots` と同じでよく、wrangler の設定（インフラ）を変えずに済むため。
2. **友達1人分の `GET /friends/{friendId}/availabilities` には付けない**：読むのは1人分で、「みんな」よりずっと軽い。友達の一覧から詳細を次々に開く使い方を止めないため。
3. **リンクのプレビューの DNS rebinding は、受け入れたリスクのまま変えない**（T-08 決定事項2の再確認）。
   - 指摘：名前解決の検査（DoH）と実際の取得（`fetch`）で名前解決が2回走るので、検査した IP と接続する IP が同じとは限らない（`apps/api/src/link-preview/infra/fetcher.ts` の `checkHost` と `deps.fetch`）。
   - 変えない理由：
     - Workers の `fetch` は接続先の IP を指定できず、接続した IP も応答から読めない。検査した IP に固定することも、取得の後に確かめることもできない。
     - Workers は Cloudflare のエッジから外に出るので、内部のアドレスに向いても、届く先は利用者側のネットワークではない。`global_fetch_strictly_public` で自分のゾーンも外からの要求として扱う。
     - 検査は「明らかに内部を向く URL を取りに行かない」ための多重の防御で、リダイレクト先も毎回検査し、本文の大きさ・時間・種類の上限もある。
   - 状況が変わったら見直す：Workers の `fetch` が接続先の IP を固定する手段や、接続した IP を返す手段を持ったとき。
4. **認証の経路（`/auth/refresh`・`/auth/complete`・`/auth/google/callback`・`/auth/apple/callback`）には、回数の上限を付けない**（T-10「付けない経路と理由」の再確認）。
   - 指摘：認証なしで呼べるので、D1 への読み書きを無制限に叩かれる余地がある。
   - 変えない理由：
     - どれも1回限りの値（state・完了コード・更新用トークン）を消費する。トークンはハッシュで引くので、1回の処理は軽く、推測もできない。連打しても書き込みは増えない。
     - `/auth/refresh` はページを開くたびに呼ばれ、失敗するとログアウトに見える。
     - IP でまとめて数えると、学校・会社・携帯の回線で同じ IP の他人が、ほかの人のログインを止められる。
     - 大量の要求そのものは、Cloudflare の WAF とレート制限のルール（pryusei/kokohima-app#42）で受ける。
   - 状況が変わったら見直す：これらの経路の失敗が `rate_limited` 以外のログ（T-13 の監視）で目立って増えたとき。

## 認可と秘匿
- 閲覧者IDの使い方：変えない。回数は閲覧者の利用者 ID で数える（`c.var.viewer.userId`）。
- 他人のデータに届かないことの保証：検索の SQL は変えない。既存の「他人のIDでは取得できない」テストがそのまま通ることで確かめる。
- 区別させない応答：429 は呼んだ人の回数だけで決まり、友達の有無や「見せない」の設定、ここ暇の有無では変わらない。

## テスト計画

### 単体テスト（実装PRで必須）
- [ ] 正常系：上限の内なら、いままでどおり200で一覧を返す
- [ ] 上限：同じ利用者が上限を超えると429 `rate_limited`、`Retry-After: 60`、Problem Details の形（テストの道具 `limiter` で上限を差し替える）
- [ ] 上限：キーが `friend_availabilities:<利用者ID>` で、別の利用者・別のまとまり（`free_slots`）の回数に影響しない
- [ ] 上限：未認証の呼び出しは401で、回数に数えない
- [ ] ログ：超えたときのログに、まとまりの名前だけが出て、利用者 ID が出ない

- [ ] 画面：429 のとき取り直さない
- [ ] 画面：前に読めた内容があれば出したまま、失敗の文言を出さない。なければ「少し時間をおいて、もう一度開いてください」を出す
- [ ] 画面：429 以外の失敗は、いままでどおり「読み込めませんでした。…」を出す

### E2Eテスト（対象にする利用者の流れ）
- 対象なし。E2E では回数の上限を実質なしにしている（T-10）。既存の E2E（「みんな」を開く流れを含む）が通ることで、流れが壊れていないことを確かめる。

## スコープ外
- `GET /friends/{friendId}/availabilities` への上限（決定事項2）。
- 認証の経路への上限（決定事項4）。
- リンクのプレビューの取得の仕組みの変更（決定事項3）。
- 「みんな」の検索の軽量化（友達全員を展開してからページに分ける作りを、SQL で絞る形に変えること）。
- フロントエンドの `staleTime`・`refetchOnWindowFocus` の見直し。
