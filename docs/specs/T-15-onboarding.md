# T-15 仕様書：初回設定（表示名・アイコン・連携の案内・通知の許可）

- 関係する要件：F-01、F-02、F-08、未決事項「表示名・アイコン・プロフィール項目、居住エリアの持ち方」（pryusei/kokohima-app#43）

## T-31 との関係（先に読む）
- 表示名を最初のログインで必須にすることと、最初の流れ（名前の画面と、友達になった直後の1画面）は、T-31（docs/specs/T-31-display-name-first-step.md。実装済み）で置き換えた。下の「振る舞い」の `/welcome` の流れ（表示名とアイコン → カレンダー連携の案内 → 通知の許可）は**行わない**。
  - 名前の画面は URL を持たず、表示名が空のあいだ、開こうとした画面の代わりに出る。招待の受け口では、名前の入力と「これで友達になる」を1つの画面にした
  - `/welcome` は「友達になった直後の1画面」（ここ暇を1つ出す・お知らせを受け取る）に使う
  - アイコンとカレンダー連携の案内は、最初の流れに入れない（設定から）
- このタスクに残るのは、`GET /me` の `emailHint` と、設定のアカウントでの通知の宛先の表示。
- 確認事項3 は T-31 で閉じた（強制する。招待経由の人は、名前の入力を「友達になる」と同じ画面にした）。

## 概要
初めてログインした人に、表示名とアイコンを決めてもらい、カレンダー連携と通知の許可を案内する。今は表示名が友達タブで入れるだけで、招待を受けただけの人は未設定のままになり、お知らせや Google の予定のタイトルに「名前未設定の友達」が出る。初回設定でこれをなくす。

## 決めたこと（要求定義書の未決事項を閉じる内容）
- プロフィールの項目は、**表示名とアイコンだけ**にする。居住エリア・自己紹介などは持たない。エリアは誘いごとの任意入力（F-10）だけで、利用者の属性としては保存しない（行動の情報を減らす）。
- アイコンは、**利用者がアップロードした画像か、なし**（なしなら表示名の1文字め）。プリセットは作らない。アップロード・配信・見える範囲は docs/specs/T-27-avatar-upload.md で決める（確認事項1 への利用者の回答）。Google・Apple のプロフィール画像の取り込みはしない（友達の端末が外部の画像サーバーを呼んで情報が漏れることを避けるため）。
- 通知の宛先のメールアドレスは、これまでどおりログインのたびにプロバイダが確認済みとした値で更新する（#56）。**手入力での変更は設けない**。設定画面で、本人にだけ一部を伏せて見せる。

## API
`api-conventions` に従う。

| メソッド | パス | 認証 | 入力（Zodスキーマ名） | 出力 | 主なエラー |
| --- | --- | --- | --- | --- | --- |
| GET | `/api/v1/me` | Bearer | なし | 200：`meResponseSchema` `{ id, displayName, avatarUrl, emailHint }`（`avatarUrl` は T-27 の署名つき URL）（`emailHint` は `a***@example.com` の形。なければ `null`） | 401、404 |
| PATCH | `/api/v1/me` | Bearer | JSON：`updateMeRequestSchema` `{ displayName }`（アイコンは T-27 の `PUT`・`DELETE /me/avatar`） | 200：`meResponseSchema` | 400 `validation_failed`、401 |

- 表示名の検証は T-02 の「表示名」の節のまま（NFC、前後の空白を除く、1〜20文字、偽装できる文字は不可）。
- 他人の公開プロフィール（友達一覧・招待の受け口など）は今のとおり `{ id, displayName, avatarUrl }`。`avatarUrl` が入る相手と URL の形は T-27。

## データ
- アイコンの列（`users.avatar_url` → `avatar_id`）の置き換えは T-27 で行う。このタスクではアイコンの列を変えない。
- 「初回設定が済んだか」の印の列は持たない。`display_name IS NOT NULL` を済んだ印とする。
- `emailHint` は `users.email` から都度つくり、保存しない。

## 振る舞い
- ログイン後、`GET /me` の `displayName` が `null` なら、Web は `/welcome` に移す。表示名を保存するまで、ほかの画面（`/welcome` と、ログアウトを除く）には進めない。
- 招待リンクから来た人（`returnTo=/invite`）は、`/welcome` を済ませてから `/invite` に戻る。誰と友達になるかを確かめる画面（T-02 決定事項8）は変えない。
- `/welcome` の流れ：
  1. 表示名（必須）とアイコン（任意。T-27 の「画像を選ぶ」の部品。T-27 より先に入れるなら、アイコンの欄は出さない）
  2. カレンダー連携の案内（「連携する」→ T-06 の画面／「あとで」）。連携すると何が見えて何が見えないか（空き・埋まりだけで、予定の中身は取得しない）を1行で書く
  3. 通知の許可（「許可する」→ ブラウザの許可を求める／「あとで」）。iOS でホーム画面に追加していない場合は、先に追加を案内する。許可の確認は、ボタンを押した操作の中で行う
- 2・3 は飛ばせる。飛ばしても、設定画面から同じことができる。
- 設定画面の「アカウント」に、表示名・アイコンの変更と、通知の宛先（`emailHint`）を表示する。宛先が `null`（メールをくれないプロバイダなど）なら「メールの通知は届きません」と静かに表示する。
- 表示名を変えても、過去のお知らせ・予定には反映しなくてよい（Google カレンダーのタイトルは、成立時の名前のまま）。

## 認可と秘匿
- 閲覧者IDの使い方：`GET`・`PATCH /me` は、アクセストークンの `sub` の行だけを読み書きする。パスや body に利用者IDを取らない。
- 他人のデータに届かないことの保証：`PATCH /me` は閲覧者自身の行だけを更新する。他人の `emailHint` は返さない。公開プロフィールにメールアドレスを含めない。
- 区別させない応答：該当なし（友達関係・公開設定に関わる応答は変えない）。
- ログ：表示名・メールアドレスを出さない。

## テスト計画

### 単体テスト（実装PRで必須）
- [ ] `GET /me`：`emailHint` を返す。メールがなければ `emailHint` は `null`
- [ ] `PATCH /me`：表示名を変えられる（アイコンは T-27）
- [ ] 入力検証：空の body は400。表示名の規則（T-02）は変わらない
- [ ] 他人のIDでは取得・更新できない（body に別の `id` を入れても、自分の行だけが変わる）
- [ ] 公開プロフィールにメールアドレス・`emailHint` が含まれない
- [ ] フロント：`displayName` が `null` なら `/welcome` に移り、保存するまでほかの画面へ進めない
- [ ] フロント：招待経由は `/welcome` のあと `/invite` に戻る
- [ ] フロント：連携・通知の「あとで」で飛ばせる

### E2Eテスト（対象にする利用者の流れ）
- [ ] 新しい利用者がログイン → 表示名とアイコンを決める → 連携・通知を飛ばす → 友達タブが開く
- [ ] 招待リンクで来た新しい利用者が、初回設定のあと「友達になる」まで進める
