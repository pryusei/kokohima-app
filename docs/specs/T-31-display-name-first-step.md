# T-31 仕様書：表示名を最初のログインで必須にし、友達になった直後の1画面を出す

- 状態：実装済み
- タスク票：docs/tasks/T-31-display-name-first-step.md
- 関係する要件：F-01、F-08、受容したリスク「友達追加の通知からの公開オフ」、未決事項「表示名・アイコン・プロフィール項目」（pryusei/kokohima-app#179、親 #178）

## 概要
招待を受けた人は、表示名が空のまま友達になれてしまい、発行者の友達一覧やお知らせに「名前未設定の友達」が並ぶ。名前がないと、友達追加の通知で「誰と友達になったか」がわからず、公開をオフにする対策（要求定義書の受容したリスク）が効かない。そこで、表示名を最初のログインで必須にし、招待の受け口では名前の入力を「友達になる」の確かめ（T-02 決定事項8）と1つの画面にまとめる。友達になった直後には、「ここ暇を1つ出す」と「お知らせを受け取る」だけの1画面を出す。

## T-15 との関係
- T-15（docs/specs/T-15-onboarding.md。下書き）の `/welcome` の流れ（表示名とアイコン → カレンダー連携の案内 → 通知の許可）のうち、**表示名を必須にすることと最初の流れは、このタスクで置き換える**。
  - 名前の画面は URL を持たない（下の「名前の画面」）。`/welcome` は「友達になった直後の1画面」に使う
  - アイコンは最初の流れに入れない（設定のアカウントで変えられる。T-27）
  - カレンダー連携の案内は最初の流れから外す（設定のカレンダー連携から。T-06）
- T-15 の確認事項3（表示名が未設定の人を進ませない強制でよいか）は、このタスクで「強制する。招待経由の人は、名前の入力を『友達になる』と同じ画面にして手数を増やさない」と決める。
- T-15 に残るのは、設定のアカウントの通知の宛先（`emailHint`）の表示など。T-15 の仕様書はそのように直す。

## API
`api-conventions` に従う。新しい経路は足さない。

| メソッド | パス | 認証 | 入力（Zodスキーマ名） | 出力 | 主なエラー |
| --- | --- | --- | --- | --- | --- |
| POST | `/api/v1/invite-links/accept` | Bearer＋Origin | JSON：`acceptInviteRequestSchema`（変更なし） | 201／200：`acceptInviteResponseSchema`（変更なし） | 404、409 `invalid_state`（自分のリンク、**または閲覧者の表示名が未設定**）、401 |

- `accept` は、自分のリンクの判定（T-02 の手順3）と発行者の確認（発行者がいなければ今のとおり404）のあとで、閲覧者の表示名が未設定（`null`）なら409 `invalid_state` を返し、友達にしない。表示名が空の友達を新しく作らないため（画面の確かめに頼らず、サーバーで保証する）
- このときは招待Cookieを消さない。名前を決めてから同じ画面で `accept` をやり直せるようにするため
- 名前の保存は今の `PATCH /api/v1/me` `{ displayName }`（T-02「表示名」の規則のまま）を使う。名前と `accept` を1つの経路にまとめない（`PATCH /me` はほかの画面でも使い、`accept` は Cookie を扱うため）

## データ
- テーブル・列の追加なし。マイグレーションなし。
- 「名前の画面が済んだか」の印は持たない。`users.display_name IS NOT NULL` を済んだ印とする（T-15 と同じ）。
- 既存の利用者で表示名が空の人のデータは書き換えない。次に開いたときに名前の画面を出す（下）。

## 振る舞い

### 名前の画面（招待を経由しないとき）
- ログイン済みの画面（`/auth/complete`・`/invite`・`/privacy`・`/terms`・`/login` を除くすべて）を出す前に、`GET /me` を読む。
  - 読み込み中は読み込み中の表示。失敗したときの読み直しは1回まで。オフラインでも待ち続けずに失敗として扱う（読み込み中のまま止めない）
  - `displayName` が `null` なら、開こうとした画面の代わりに名前の画面を出す。URL は変えない（保存すると、そのまま開こうとした画面が出る。ログインの `returnTo` を失わない）。
  - 読み込めなかった（通信エラーなど）ときは、名前の画面で止めず、いつもの画面を出す。
- 新しい利用者（最初のログイン）も、既存の利用者で表示名が空の人（次に開いたとき）も、同じ名前の画面になる。
- 名前の画面の中身：
  - 見出し「表示名を決めてください」
  - 説明の1行「友達に見える名前で、あとで設定から変えられます。」
  - 欄「表示名」（1つ）と「これで始める」。空白だけのあいだは押せない
  - 保存できなかったら「保存できませんでした。1〜20文字で入力してください。」と静かに出す（赤を使わない）
  - 下に「ログアウト」（ほかの画面に進めないので、ここから出られるようにする）。できなかったら「ログアウトできませんでした。通信状態を確認して、もう一度お試しください。」（設定のアカウントと同じ）

### 名前の画面（招待リンクの受け口。「友達になる」の確かめと兼ねる）
- `/invite` で発行者が出ていて（`lookup` が成功）、ログイン済みのとき、`GET /me` を読む。
  - 読み込み中は、ボタンの位置に読み込み中の表示。読み直しとオフラインの扱いは上の名前の画面と同じ。
  - `displayName` があれば、今のとおり「友達になる」（T-02）。押したあとも今のとおり友達タブへ移る。
  - `displayName` が `null` なら、「友達になる」の代わりに、欄「あなたの表示名」（1つ）と「これで友達になる」を出す。発行者の名前・アイコンと説明の1行（T-02 のまま）はそのまま出し、説明の文を足さない。空白だけのあいだは押せない
  - 読み込めなかったときは「通信できませんでした。通信状態を確認して、リンクをもう一度開いてください。」（`lookup` の通信エラーと同じ文言）を出し、ボタンは出さない（名前があるかわからないまま `accept` しない）。
- 「これで友達になる」を押すと、`PATCH /me` で名前を保存し、続けて `accept` を呼ぶ（1回押すだけ。決定事項8 の「1回押す」を満たす）。
  - 名前の保存に失敗したら（400 など）、`accept` を呼ばず、欄の下に「保存できませんでした。1〜20文字で入力してください。」と静かに出す。欄はそのまま直せる
  - 名前を保存して `accept` が失敗したときは、今の受け口と同じ文言（404・409・通信エラー。T-02）を出す。名前は保存されたまま
  - `accept` が成功したら、友達になった直後の画面（`/welcome`）へ移る（履歴は置き換える）
- 発行者が自分のリンクを開いたとき（409）の扱いは変えない。表示名がない人は招待リンクを発行できないので（T-02）、名前の画面と「自分のリンク」は同時に起きない。

### 友達になった直後の1画面（`/welcome`）
- 招待の受け口で名前を決めて友達になったあとに出す。すでに名前があって「友達になる」を押した人には出さない（友達タブへ移る。今のとおり）。
- URL は `/welcome`（ログイン済みの画面。名前が空なら、上の名前の画面が先に出る）。直接開いても同じ画面を出す。
- 中身：
  - 見出し「友達になりました」
  - 説明の1行「どちらも、あとで設定からできます。」（この画面の説明の文はこの1行だけ）
  - 「ここ暇を1つ出す」：時間帯プリセット（昼・夕方・夜。閲覧者の今のプリセットの時刻を添える）のチップを並べる。押すと、その日のそのプリセットでここ暇を1つ作る（`POST /api/v1/availabilities` `{ date, preset }`。T-03。`Idempotency-Key` を付ける。T-10）
    - 日付は今日。今日のプリセットがすべて終わっている（終了が現在時刻以前）ときは明日にし、見出しを「明日のここ暇を1つ出す」にする（今日なら「今日のここ暇を1つ出す」）
    - 今日のうち、終わったプリセットのチップは押せない
    - 作れたら「出しました」と出し、チップは押せなくする（1つだけ）。作れなかったら（重なり・上限の409、400、通信エラー）「出せませんでした。ここ暇タブから出してください。」と静かに出す
    - プリセットの時刻を読み込むあいだは読み込み中の表示。読み込めなかったら「読み込めませんでした。もう一度お試しください」と「もう一度」（T-11 の読み込めないときの表示）
  - 「お知らせを受け取る」：
    - この端末でプッシュを受け取れるブラウザ（T-07 の `pushSupported`）なら、ボタン「お知らせを受け取る」。押した操作の中でブラウザの許可を求め、購読して登録する（T-07 と同じ手順）。受け取る状態になったら「この端末で受け取ります」、許可されなかったら「通知が許可されていません。端末の設定で許可すると受け取れます」、失敗したら「受け取れるようにできませんでした。設定の通知からお試しください。」と静かに出す。すでに受け取る状態なら、ボタンの代わりに「この端末で受け取ります」
    - 受け取れるブラウザでまだ受け取っていないときは、ボタンの上にロック画面の見え方の2択（`LockScreenPicker`、下の1行の説明は出さない `hint={false}`）を置く（T-35「画面」）
    - 受け取れないブラウザ（iOS でホーム画面に追加していないなど）なら、ボタンの代わりにリンク「ホーム画面に追加して、お知らせを受け取る」（`/settings/install`。T-25）
  - 一番下に「友達の一覧へ」（友達タブ `/friends` へ移る。履歴は置き換える）。どちらもしないで押してよい（飛ばせる）
- カレンダー連携の案内は出さない。

### 説明の文
- 名前の画面（2つ）と直後の画面は、それぞれ説明の文を1行までにする（見出し・欄の名前・ボタン・操作の結果の文言は数えない）。

### 友達タブの招待リンクの節
- 表示名が未設定の人は名前の画面から先に進めないので、友達タブの「招待リンクを作る」のシートで表示名の入力に置き換える処理（T-02「表示名」）はなくす。発行の API が名前のない人に409を返すことは変えない。

## 認可と秘匿
- 閲覧者IDの使い方：`accept` は `requireAuth` の閲覧者IDの表示名だけを見る（`getPublicProfiles(ctx, viewerId, [viewerId])`。発行の判定と同じ）。`PATCH`・`GET /me` は今のとおりアクセストークンの `sub` の行だけを読み書きする。
- 他人のデータに届かないことの保証：新しい経路はない。`accept` の判定に他人の表示名は使わない。名前の画面の保存は閲覧者自身の行だけを更新する（T-02 のテストのまま）。
- 区別させない応答：表示名が未設定の409は、閲覧者自身の状態だけで決まり、リンクの有無・期限・発行者についての情報を増やさない（使えないリンクは、今のとおり名前の判定より前に404）。
- ログ：表示名を出さない。

## テスト計画

### 単体テスト（実装PRで必須）
- [x] API：表示名が未設定の閲覧者の `accept` は409 `invalid_state` で、友達にならず、人数を消費せず、招待Cookieを消さない。名前を決めると同じCookieで友達になれる
- [x] API：使えないリンク（Cookieなし）は、名前が未設定でも今のとおり404（名前の判定より前）
- [x] API：発行者がいなくなったリンクは、名前が未設定でも404（名前の判定より前）
- [x] フロント：`displayName` が `null` なら、どの画面（例：`/availability`）でも名前の画面が出て、保存すると開こうとした画面が出る（URL は変わらない）
- [x] フロント：名前の画面の保存の失敗は静かな文言で、画面に留まる
- [x] フロント：`GET /me` が読めないときは名前の画面で止めない（読み直しの設定を既定のままにした QueryClient でも、1回の読み直しのあとに画面を出す）。読み込み中は読み込み中の表示
- [x] フロント：招待の受け口で名前がないと、欄と「これで友達になる」が出る。押すと `PATCH /me` → `accept` の順に呼び、`/welcome` へ移る
- [x] フロント：受け口の名前の保存に失敗したら `accept` を呼ばない
- [x] フロント：名前があれば今のとおり「友達になる」で友達タブへ（`/welcome` に移らない）
- [x] フロント：直後の画面：チップで今日のプリセットのここ暇を作り（`Idempotency-Key` つき）、「出しました」と出す。終わったプリセットは押せない。今日がすべて終わっていたら明日になる
- [x] フロント：直後の画面：受け取れるブラウザなら「お知らせを受け取る」で許可と登録、受け取れないブラウザならホーム画面に追加する案内へのリンク。登録に失敗したら静かな文言
- [x] フロント：直後の画面：プリセットを読み込めなければ「もう一度」で読み直せる
- [x] フロント：直後の画面：「友達の一覧へ」で何もせずに友達タブへ移れる。説明の文は1行
- [x] 他人のIDでは取得・更新できない：新しい経路はなく、`PATCH /me` が閲覧者自身の行だけを更新するテスト（T-02）のまま

### E2Eテスト（対象にする利用者の流れ）
- [x] 招待リンクを開く → 名前のないユーザーでログイン → 名前を入れて「これで友達になる」 → 直後の画面でここ暇を1つ出す → 「友達の一覧へ」で友達タブに発行者が出る。発行者の友達一覧に、入れた名前が出る
- [x] 名前のないユーザーでアプリを開くと名前の画面が出て、決めると「みんな」が開く
- 「お知らせを受け取る」は、ブラウザの通知の許可の画面を E2E で扱えないため単体テストで確かめる
- テスト用ログイン済みのページ（`loggedInPage`）は、名前の画面を通らないよう表示名つきのユーザーにする

## スコープ外
- LINE の名前を表示名の下書きに入れること（LINE ログインがまだないため。確認事項1）
- アイコンの初回設定、カレンダー連携の案内（設定から）
- 設定のアカウントの通知の宛先（`emailHint`）の表示（T-15 に残す）
- 既存の利用者の表示名の一括の補完（次に開いたときに名前の画面で入れてもらう）

## 確認事項（合意前に解消する）
1. LINE の名前を表示名の下書きに入れるか（1手減るが、本名が出やすい）。LINE ログインを入れるときに決める（issue #179「決めること」）
2. 直後の画面を、すでに名前がある人が友達になったときにも出すか。今は「名前の画面を通った人だけ」にした（名前のある人は、もう使い始めているとみなす）
3. 名前の画面からは退会に進めない（ログアウトだけ）。表示名を決めずに退会したい人には、いったん名前を決めてから設定で退会してもらう形でよいか
