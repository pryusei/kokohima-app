### 5. 制定日の検査
- 本文の制定日の行は、文字列の定数1つ（`apps/web/src/pages/legal.ts` の `EFFECTIVE_DATE_LINE = "制定日：2026年11月23日"`）を2つのページで使う。「制定日：」と日付を分けた文字列にしない（分けると、ビルドした JS の中で別々の文字列になり、下の検査で並びを見られない）。定数は1つの module にあるので、ビルドした JS に「制定日：」は1回だけ入る（ページごとではない）。
- 検査は「◯」を探すのでなく、本物の日付の形を確かめる。純粋な関数を `apps/api/scripts/lib/effective-date.mjs` に置く（`node:fs` などを使わず、文字列だけを受け取る）。
  - `countEffectiveDateLines(text)`：「制定日：」の数を返す。
  - `countRealEffectiveDates(text)`：`/制定日：(\d{4})年(\d{1,2})月(\d{1,2})日/g` に当たり、かつ暦にある日付（`Date.UTC` で作り直して年月日が同じ。`2026年13月40日`・`2026年2月30日` は数えない）の数を返す。
  - 改定日も同じ形：`countRevisionDateLines(text)`（「改定日：」の数）と `countRealRevisionDates(text)`。改定日の行は `legal.ts` の `REVISION_DATE_LINE`（`string | null`。初めて改定するまで `null`。「8.」）。
  - 型は隣の `effective-date.d.mts` に書く（TS のテストから読むため）。
- `check-web-dist.mjs`（`dist` の `.js` のファイルを読み、上の関数に渡す）：
  - いつも（CI の `build:prod` の `check:release` でも）：「制定日：」が `dist` の全体で、ちょうど1回（`EXPECTED_EFFECTIVE_DATE_LINES = 1`）。0回（文言を変えた・ページが入っていない）や2回以上（分けて書いた）なら止める。これで、毎回の本物のビルドの出力で形を確かめる。
  - いつも：「改定日：」は0回か1回（`MAX_REVISION_DATE_LINES = 1`）。2回以上なら止める。
  - `--deploy` のときだけ（`deploy:prod` は `check-web-dist.mjs --deploy` を呼ぶ）：さらに、制定日が本物の日付でちょうど1回。改定日があれば、それも本物の日付。仮の値（「◯」）、形の違う日付、暦にない日付なら止める。
  - 今の検査（インラインの script・style、E2E の名前、Apple のボタン）は変えない。
- テストの置き場：CI の `pnpm test` はルートの `vitest run`（`projects: ["apps/*", "packages/*"]`）で、`apps/api` は Workers の project（`apps/api/vitest.config.ts`。`include` の指定がないので、`apps/api` の下の `*.test.ts` をすべて読む）。新しい project は足さず、この Workers の project でテストする。関数は `node:fs` を使わない純粋な関数なので、Workers のランタイムでも動く。
  - テストは `apps/api/test/effective-date.test.ts`（`apps/api/tsconfig.json` の `include` の `test` に入る。`scripts/` は `include` に入っていないが、テストが読む `.mjs` の型は隣の `.d.mts` で解決する）。`scripts/` の下にはテストを置かない（`.mjs` の検査のスクリプトと同じ場所に TS のテストを混ぜない）。
  - 入力は、ビルドの出力の形をまねた fixture：`apps/api/test/fixtures/web-dist-legal.js`（vite が圧縮した chunk のように、1行に `const E="制定日：2026年◯月◯日";` と、ほかの文字列が並ぶもの。テストでは `?raw` で読む。`apps/api/test/raw.d.ts` のとおり）。仮の値・本物の日付・2回入ったもの・「制定日：」がないものを、fixture の文字列を置き換えて作る。
  - ESLint：`apps/api/scripts/lib/effective-date.mjs` は今の設定の `**/scripts/**/*.{js,mjs}`（node の globals）で、テストの `.ts` は `typescript-eslint` の推奨の設定で lint される。ESLint の設定の変更は、fixture のために `apps/api/test/fixtures/**` を `ignores` に足すことだけ（圧縮した形をまねるため）。

- Google アカウントの識別子（Google がアカウントごとに発行する番号）
- Google で確認済みのメールアドレス
- Google アカウントの名前・プロフィール写真・パスワードは受け取りません。

### あなたが入力するもの
- 表示名（アイコンの画像は持ちません。アイコンには表示名の1文字めを出します）
- ここ暇（誘っていい時間の範囲）、くり返し（カレンダーの予定で外れた日を含みます）、時間帯プリセット
- 友達ごとの「見せる／見せない」の設定
- 誘い・募集の内容（相手、日時、エリア、ひとこと、リンク）、返事、成立した予定
- 友達の関係と、発行した招待リンク（リンクの鍵は、元に戻せない形でだけ保存します）
- タイムゾーン（今は、すべての人が日本時間です）

### カレンダーを連携した人から受け取るもの
- Google カレンダーの、空き／埋まりの時刻だけ。予定のタイトル・場所・参加者・説明は、取得も保存もしません。
- Google から受け取る許可（更新用のトークン）。暗号化して保存します。
- このサービスがあなたの Google カレンダーに作った「ここ暇」カレンダーの識別子

### 通知のためのもの
- お知らせ（アプリの中で読む通知）と、通知の設定
- プッシュ通知の宛先（ブラウザが発行する URL）。暗号化して保存します。

### 使うときに自動で生まれるもの
- ログインの記録：ログインした時刻と、最後に使った時刻
- 新しい端末でのログインに気づくための、ブラウザ名と OS 名の要約（例：「Safari / iOS」）。新しい端末でのログインのお知らせと、その処理の記録に入ります。ブラウザが送る情報（User-Agent）の全文と IP アドレスは保存しません。
- IP アドレス：短い時間に同じ操作がくり返されていないかの判定に使います。このサービスのデータベースには保存しません。
- 動作の記録（ログ）：障害や不正に気づくための記録です。利用者を区別する番号が入ることがありますが、メールアドレス・名前・ひとこと・トークン・カレンダーの認証情報は入れません。
- 処理の記録：通知やカレンダーへの書き込みなど、あとで行う処理の記録です。誰がどの誘いに返事をしたかなどが入ります。
- 二重の送信を防ぐための記録：同じ操作が2回届いたときに、1回目と同じ結果を返すための記録です。送った誘いなどの内容が入ります。

## 3. 使う目的
1. ログインと、本人の確認のため
2. 友達どうしで「ここ暇」を見せ合い、誘い・募集・返事をやりとりするため
3. 成立した予定を、連携したカレンダーに書き込み、カレンダーのファイル（.ics）で渡すため
4. 連携したカレンダーに予定が入ったとき、重なる「ここ暇」を自動で取り消し、空いている時間を候補として出すため
5. 誘い・予定・友達の追加などを、お知らせ・プッシュ通知・メールで知らせるため。新しい端末でのログインを、メールで知らせるため
6. 誘い・募集に付けたリンクの、タイトルと画像のプレビューを作るため
7. 不正な利用を防ぎ、障害に気づいて直すため
8. この規約・ポリシーの大事な変更など、運営からの大事なお知らせを送り、問い合わせに答えるため

メールアドレスは、5.のお知らせのメール、8.の運営からの連絡、「12.」の求めでの本人の確認にだけ使います。

このサービスは、広告を出しません。預かった情報を売りません。アクセス解析のツールも使いません。

## 4. ほかの利用者に見えるもの
- 友達になるのは、招待リンクを開いて「友達になる」を押したときだけです。友達でない人に、あなたの「ここ暇」は見えません。
- 友達には、あなたの表示名と、「見せる」にした友達にだけ「ここ暇」（時刻の範囲だけ）が見えます。「見せない」にした友達には、暇がないときと同じに見えます。
- 誘いの相手には、送った内容（日時・エリア・ひとこと・リンク）と返事が見えます。
- 募集では、募集した人に見えるのは、応じた人の数だけです。応じた人の名前は、募集した人が「決める」まで、誰にも見せません。「決める」と、成立した予定の参加者どうしには、友達でなくても、おたがいの表示名が見えます。
- 招待リンクを開いた人には、リンクを発行した人の表示名が見えます。
- 予定が成立すると、Google カレンダーを連携している参加者の「ここ暇」カレンダーに、ほかの参加者の表示名・日時・エリアを書き込みます。.ics のファイルにも同じ内容が入ります。書き込んだ予定は、その参加者の Google アカウントの中にあります。終わった予定は消さないので、あとから運営が消すことはできません。
- 退会すると、相手の履歴には「退会したユーザー」と出ます。

## 8. 保存する期間
- アカウント（メールアドレス・表示名・タイムゾーン・Google の識別子）、友達、設定、くり返し：退会したときに消します。
- ここ暇の枠：始まってから2日で消します（枠は最長1日なので、終わってから1〜2日です）。
- くり返しの、予定で外れた日の記録：その日から3日目に消します。
- 誘い・募集・成立した予定：予定の時間（「この時間なら」で代わりの時間があれば、遅い方）が終わってから30日で消します。
- お知らせの日ごとの数（1日に送る通知の上限を数えるため）：その日から4日目に消します。
- お知らせ：作ってから30日で消します。新しい端末でのログインのお知らせに入る、ブラウザ名と OS 名の要約も同じです。
- 招待リンク：期限から30日で消します。
- ログインの記録：使えなくなってから30日で消します。新しい端末でのログインに気づくため、最初のログインの記録だけは退会まで残します。
- プッシュ通知の宛先：ログアウトしたとき、届けられなくなったとき、ログインが切れたとき、退会したときに消します。
- カレンダーの許可：連携を解除したとき、Google 側で許可が取り消されたとき、退会したときに消します。
- カレンダーの連携の記録（連携したことと、その状態）と、「ここ暇」カレンダーの識別子：連携を解除しても残し、退会したときに消します（もう一度連携したときに、同じ「ここ暇」カレンダーを使うため）。
- カレンダーの空き／埋まりの記録：連携を解除したとき、30日アプリを開かなかったとき、退会したときに消します。
- カレンダーの空き／埋まりの一時的な記録：5分で消えます。連携を解除しても、最長5分は残ります。
- リンクのプレビュー：使う誘い・募集がなくなり、取ってから30日を過ぎたら消します。
- リンクのプレビューの画像：使うプレビューがなくなってから1時間で消します。
- 処理の記録：処理してから7日で消します。まだ送り始めていない通知の記録は、作ってから30日で消します。うまく処理できなかった記録は4日で消えます。
- 二重の送信を防ぐための記録：24時間で消します。
- ログ：7日で消えます。
- データベースの復元用の記録：消したあとも、最大30日は復元のための記録に残ります。
- 外部の事業者（「5.」）が持つ記録（メールの送信の記録など）は、それぞれの事業者の定めによります。

### 退会したとき
- 退会すると、すぐに名前・メールアドレス・ログイン・友達・ここ暇・設定・あなたあてのお知らせ・プッシュ通知の宛先を消します。取り消しはできません。
- 続けて、あなたが誘い・募集に書いたひとこと・エリア・リンクを消し、あなたの Google カレンダーの「ここ暇」カレンダーを消して、Google の許可を取り消します。この処理は退会のあとに自動で行い、うまくいかなかったときは、やり直します。
- これからの成立した予定は、「やっぱり難しい」を押したのと同じになります。返事を待っている誘い・募集も終わります。
- 次のものは、相手のために残り、上の期間で消えます。
  - 相手の履歴（誘い・募集・成立した予定の日時、相手、返事）。相手には「退会したユーザー」と出ます。予定の時間が終わってから30日で消えます。
  - 相手あてのお知らせ（あなたからだったことを含みます）。作ってから30日で消えます。
  - 相手に関わる処理の記録。上の「処理の記録」の期間で消えます。
  - カレンダーの空き／埋まりの一時的な記録。最長5分で消えます。
- 利用者を区別する番号と、退会した時刻だけは残します（相手の履歴を「退会したユーザー」と出すため）。

## 確認事項

### (a) 合意（この仕様書PRのマージ）の前に決める
1. **裁判所**：運営者の住所を書かないので「日本の裁判所で解決します」にした。「運営者の住所地を管轄する裁判所」などにするかは、利用者が決める（消費者の利用者には、住所地から遠い専属の管轄は認められないことがある）。
2. **大事な変更の知らせ方**：アプリの画面で全員に知らせる仕組みがない（#91）。当面は、運営が全員にメールを送るか、ほかの方法にするか。このページを初めて出すときに、すでに使っている友達に知らせるかも、ここで決める。

### (b) デプロイの前に人が確かめること
実装PRのマージのあと、`deploy:prod` の前に人が確かめる。違っていれば、仕様書PRで本文を直してからデプロイする。
1. **文言**：「6.」「7.」の文案は法律の助言ではない。利用者が全文を読み、最終の文言を決める。必要なら専門家に見てもらう。
2. **制定日**：「2026年11月23日」に決めた（利用者の回答）。
3. **運営者の氏名と住所**：個人情報保護法では、運営者の氏名（名称）と住所を、本人が知りうる状態（求めに応じて遅滞なく答える形を含む）に置くことになっている。「求められたときに、遅滞なくお知らせします」で足りるかを確かめる。
4. **外国にある第三者への提供の中身**：方法は相当措置に決めた（決めたこと11）。この作業環境からは事業者と個人情報保護委員会のサイトを読んでいないので、本文の「5.」「6.」「7.」の次の事実を公式の資料で確かめる。合わない文は、仕様書PRで直すか消す（言い過ぎない）。
   - Cloudflare の DPA：運営のアカウントに当てはまること、相当措置の項目（任された目的の範囲での取り扱い、安全管理の措置、従業者と再委託先の監督、漏えいの報告、再提供の制限、契約が終わったときの扱い。個人情報保護委員会のガイドライン（外国にある第三者への提供編）の相当措置の項目）を満たすこと。
   - Google：ログイン（OAuth）とカレンダー API に当てはまる規約・条件の名前（Google API の利用規約、ユーザーデータに関するポリシー、そのほかのデータ保護の条件があるか）と、相当措置の項目を満たすか。成立した予定の書き込み（ほかの参加者の表示名など）を Google に渡すことの扱いも確かめる。
   - Resend：DPA があり運営のアカウントに当てはまること、相当措置の項目を満たすこと（正式な名称と国は5.とあわせて）。
   - ブラウザのプッシュ通知の事業者：それぞれの条件の名前と、宛先と中身のない合図だけを渡すという書き方でよいか。
   - Slack・Better Stack：本当に個人データを渡していないか（8.とあわせて）。
   - Cloudflare：D1・R2・KV のデータを保管する場所（場所の指定があるか）と、「世界各地の拠点で処理し、国を前もって特定できない」という書き方。
   - 個人情報保護委員会の調査：正式な名称・最新版・URL と、米国の概要の要約（包括的な法律がない、FTC 法5条による取り締まり、分野ごとの法律・州の法律、政府が事業者に情報の提供を求められる制度）が調査の記載に合い、中立であること。URL のリンクを付けるか（付けるなら外へのリンクの扱いは「3.」のとおり）。
   - 確かめ続けること：「年に1回と、条件の変更を知ったとき」を運営が実際に行えること。デプロイの前に1回めを行い、「支障は見つかっていません」が本当であること。
   - 求めに応じて知らせる事項（施行規則18条3項）が、本文と、求めへの答え方でそろっていること。
5. **Resend**：送信の拠点が東京であること（利用者から聞いた値。リポジトリの仕様書には書かれていない）、事業者の正式な名称と国、送信の記録の保存期間（#89）を、Resend の管理画面と規約で確かめる。
