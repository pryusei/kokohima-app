### 1. 経路と描画
- 経路は `/privacy`（プライバシー ポリシー）と `/terms`（利用規約）。
- 本番では、`not_found_handling: single-page-application`（T-12）で `index.html` が返るので、直接開いても、再読み込みしても画面が出る。wrangler の設定は変えない。
- `apps/web/src/App.tsx` で、ログインの状態を見る前に描画する（今の `/invite` と同じ位置）。ログインの確認中（`checking`）、API に届かない（`error`）、ログインしていない（`anonymous`）、ログインしている（`authenticated`）のどれでも、別の画面に移さず本文を出す。
- 画面は `apps/web/src/pages/PrivacyPage.tsx` と `TermsPage.tsx`（共通の形・見出し・リンクの部品とログイン画面などの1行は `apps/web/src/pages/LegalDocument.tsx`）。本文は JSX のテキストで書く（`dangerouslySetInnerHTML` や Markdown の変換は使わない。CSP と XSS の対策のまま）。
- 2つのページは遅延読み込み（`React.lazy`）にし、別のチャンクにする（T-49。docs/specs/T-49-perf-small-fixes.md「4.」）。本文が合わせて約42kB あり、開く人が少ないため。読んでいる間はログインの確認中と同じ読み込み中の形を出し、チャンクを読めなければ静かな文言と「もう一度」（ページを読み直す）を出す。共通の部品（`LegalDocument.tsx`・`legal.ts`）はログインの画面が使うので、最初のチャンクに残る（制定日などの行の検査は、すべての JS を合わせて数えるので変わらない）。

### 5. 制定日・改定日の検査
- 本文の制定日の行は、文字列の定数1つ（`apps/web/src/pages/legal.ts` の `EFFECTIVE_DATE_LINE = "制定日：2026年11月23日"`）を2つのページで使う。「制定日：」と日付を分けた文字列にしない（分けると、ビルドした JS の中で別々の文字列になり、下の検査で並びを見られない）。定数は1つの module にあるので、ビルドした JS に「制定日：」は1回だけ入る（ページごとではない）。
- 検査は「◯」を探すのでなく、本物の日付の形を確かめる。純粋な関数を `apps/api/scripts/lib/effective-date.mjs` に置く（`node:fs` などを使わず、文字列だけを受け取る）。
  - `countEffectiveDateLines(text)`：「制定日：」の数を返す。
  - `countRealEffectiveDates(text)`：`/制定日：(\d{4})年(\d{1,2})月(\d{1,2})日/g` に当たり、かつ暦にある日付（`Date.UTC` で作り直して年月日が同じ。`2026年13月40日`・`2026年2月30日` は数えない）の数を返す。
  - 改定日も同じ形：`countRevisionDateLines(text)` と `countRealRevisionDates(text)`。改定日の行は `legal.ts` の `REVISION_DATE_LINE`（`string | null`。仕様書の8節）。
    - 改定の実装PRで、数える文字を「改定日：」から「改定日（効力が生じる日）：」に変える（決めたこと14。行の文字列が変わるため）。
  - 改定の実装PRで、予告の行を足す：`countRevisionNoticeLines(text)`（「公表日：」の数）と `countRealRevisionNoticeDates(text)`。予告の行は `legal.ts` の `REVISION_NOTICE_LINE`（`string | null`。「公表日：YYYY年M月D日（この版は改定日から適用します。それまでは、前の版を適用します）」の1つの文字列。予告の間だけ入れ、ほかのときは `null`）。
  - 型は隣の `effective-date.d.mts` に書く（TS のテストから読むため）。
- `check-web-dist.mjs`（`dist` の `.js` のファイルを読み、上の関数に渡す）：
  - いつも（CI の `build:prod` の `check:release` でも）：「制定日：」が `dist` の全体で、ちょうど1回（`EXPECTED_EFFECTIVE_DATE_LINES = 1`）。0回（文言を変えた・ページが入っていない）や2回以上（分けて書いた）なら止める。これで、毎回の本物のビルドの出力で形を確かめる。
  - いつも：「改定日（効力が生じる日）：」は0回か1回（`MAX_REVISION_DATE_LINES = 1`）。2回以上なら止める。
  - いつも（改定の実装PRで足す）：「公表日：」は0回か1回。改定日の行がないのに「公表日：」があれば止める。前の形の「改定日：」が残っていれば止める。日付の大小は見ない（CI の結果が、走らせた日で変わらないように）。
  - `--deploy` のときだけ（`deploy:prod` は `check-web-dist.mjs --deploy` を呼ぶ）：さらに、制定日が本物の日付でちょうど1回。改定日・公表日があれば、それも本物の日付。仮の値（「◯」）、形の違う日付、暦にない日付なら止める。
  - `--deploy` のときだけ（改定の実装PRで足す）：日付の大小を確かめる。今日（T）は、`check-web-dist.mjs` がデプロイする時刻の日本時間の日付として作り、`effectiveDateProblems(texts, { deploy, today, noticeAlreadyPublished })` に渡す（関数は純粋なまま。`today` は `{ year, month, day }`）。改定日を R、公表日を P、制定日を E とする。日数の差は `Date.UTC` で作った日付の差で数える。
    - 予告の間（公表日の行がある）：P ≦ T ≦ R、かつ R − P が7日以上30日以下。P がデプロイの日より後（未来の公表日）、予告が7日より短い・30日より長い、改定日を過ぎても予告の行が残っている、のどれかなら止める。
      - 初めて予告を出すデプロイ（本番にまだこの予告の行が出ていない）では、P ＝ T を求める。公表日より後に初めてデプロイすると、予告が短くなり、ページの公表日も実際と違うため。本番にもう出ていれば（予告の間のほかのデプロイ）、P ≦ T のまま。
      - 本番に出ているかは、`check-web-dist.mjs` が本番の画面（`https://kokohima.app/`。`apps/api/scripts/lib/published-notice.mjs` の `PRODUCTION_ORIGIN`）の `index.html` を読み、そこから読み込む同じオリジンの JS（`script` の `src`・`modulepreload`、その JS が読み込む chunk）に、ビルドした予告の行の文字列（`REVISION_NOTICE_LINE` の全体）がそのまま入っているかで決め、`noticeAlreadyPublished` として渡す。日付をずらした予告は別の文字列なので、初めて出すデプロイとして扱う。
      - 本番を読めない（通信の失敗、200 でない、`index.html` が HTML でない、JS の `Content-Type` が JavaScript でない（SPA の振り分けで、ない JS に `index.html` が返る形）、script がない、JS が50を超える）ときは止める。確かめを飛ばす方法（フラグ・環境変数）は作らない。`noticeAlreadyPublished` が渡されないときも止める。
      - E ≦ P（制定した日に最初の改定を予告できるようにする。決めたこと16）。
    - 予告のあと（公表日の行がない）：E ＜ R ≦ T。改定日がデプロイの日より後なのに予告の行がなければ止める（前もって知らせずに未来の日付だけを書いた形）。
    - いつも（`--deploy`）：E ≦ T。
    - 今の検査では日付の大小を見ていない（`effectiveDateProblems(texts, { deploy })` は本物の日付かだけを見る）。この2つの条件が、改定の実装PRで足すもの。
    - 日本時間の今日は、`effective-date.mjs` の純粋な関数 `jstToday(now)`（ミリ秒の時刻に9時間を足した UTC の年月日）で作り、`check-web-dist.mjs` が `Date.now()` を渡す。今日を外から差し替える方法（環境変数など）は作らない。
    - `deploy` が真なのに `today` が渡されなければ、止める（大小を確かめないまま通さない）。
    - 改定日・公表日の数か形の問題（前の形の「改定日：」を含む）があるときは、改定日・公表日の大小の検査をしない（その問題だけを出す）。
  - ブロックと通報を始める日（T-33「振る舞い 8.」）：`safetyStartProblems(texts, { startDate, deploy, today })`（`packages/shared/src/safetyStart.json`）。いつも：`null` か暦にある日付でなければ止める。`--deploy` で今日が始める日より前なら、予告の行がちょうど1つあり、改定日が始める日と同じこと。
  - 問い合わせの公開の日（T-24「振る舞い 11.」）：`contactStartProblems(texts, { startDate, deploy, today, noticeAlreadyPublished, production })`（`packages/shared/src/contactStart.json` の `startDate`）。いつも：`startDate` が `null` か暦にある日付でなければ止める。`--deploy` で予告の行がある間は、改定日（効力が生じる日）が `startDate` と同じこと（今日が `startDate` 以後で、問い合わせがもう本番の本文にあるときを除く）。今日が `startDate` より前で予告がもう本番に出ているなら、本番の「この改定で変わるところ」に問い合わせの行が出ていること。本番は、予告の行と同じ1回の読み込みで調べる（`published-notice.mjs` の `findPublishedStrings`）。読めなければ止める。
  - 検査で防げないこと：予告の行を入れずに、今日の日付を改定日にした形（R ≦ T なので通る）。デプロイの前に人が確かめる（#52 の人の作業。仕様書の8節）。
  - 今の検査（インラインの script・style、E2E の名前、Apple のボタン）は変えない。
- テストの置き場：CI の `pnpm test` はルートの `vitest run`（`projects: ["apps/*", "packages/*"]`）で、`apps/api` は Workers の project（`apps/api/vitest.config.ts`。`include` の指定がないので、`apps/api` の下の `*.test.ts` をすべて読む）。新しい project は足さず、この Workers の project でテストする。関数は `node:fs` を使わない純粋な関数なので、Workers のランタイムでも動く。

## 3. 使う目的
1. ログインと、本人の確認のため
2. 友達どうしで「ここ暇」を見せ合い、誘い・募集・返事をやりとりするため
3. 成立した予定を、連携したカレンダーに書き込み、カレンダーのファイル（.ics）で渡すため
4. 連携したカレンダーに予定が入ったとき、重なる「ここ暇」を自動で取り消し、空いている時間を候補として出すため
5. 誘い・予定・友達の追加などを、お知らせ・プッシュ通知・メールで知らせるため。新しい端末でのログインを、メールで知らせるため
6. 誘い・募集に付けたリンクの、タイトルと画像のプレビューを作るため
7. 不正な利用を防ぎ、障害に気づいて直すため。問い合わせで知らせてもらった不具合を直すため。通報を受けて、危ない使い方や規約に反する使い方に対応するため
8. この規約・ポリシーの大事な変更など、運営からの大事なお知らせを送り、問い合わせに答えるため
9. 問い合わせでもらったご意見をもとに、このサービスを良くするため
10. 行きたいを置くときに、入力したエリアとしたいことから、AIで店や場所の候補を探すため

メールアドレスは、5.のお知らせのメール、8.の運営からの連絡と問い合わせへの返事（問い合わせのときは、返信先として運営の連絡用の Slack に届けます）、「12.」の求めでの本人の確認にだけ使います。

このサービスは、広告を出しません。預かった情報を売りません。アクセス解析のツールも使いません。

## 4. ほかの利用者に見えるもの
- 友達になるのは、招待リンクを開いて「友達になる」を押したときだけです。友達でない人に、あなたの「ここ暇」は見えません。
- 友達には、あなたの表示名とアイコンの画像と、「見せる」にした友達にだけ「ここ暇」（時刻の範囲だけ）が見えます。「見せない」にした友達には、暇がないときと同じに見えます。
- 誘いの相手には、送った内容（日時・エリア・ひとこと・リンク）と返事が見えます。
- 行きたいは、外した友達を除く友達に見えます（あとから友達になった人にも見えます）。誰を外したかは、外された人にも、ほかの友達にも見せません。
- 募集では、募集した人に見えるのは、応じた人の数だけです。応じた人の名前は、募集した人が「決める」まで、誰にも見せません。「決める」と、成立した予定の参加者どうしには、友達でなくても、おたがいの表示名が見えます（アイコンの画像は、友達どうしにだけ見えます）。
- 招待リンクを開いた人には、リンクを発行した人の表示名とアイコンの画像が見えます。
- 予定が成立すると、Google カレンダーを連携している参加者の「ここ暇」カレンダーに、ほかの参加者の表示名・日時・エリアを書き込みます。.ics のファイルにも同じ内容が入ります。書き込んだ予定は、その参加者の Google アカウントの中にあります。終わった予定は消さないので、あとから運営が消すことはできません。
- 退会すると、相手の履歴には「退会したユーザー」と出ます。
- ブロックや通報をしたことは、相手に知らせません。ブロックした相手には、友達を解除したときと同じに見えます。ブロックしている間は、どちらの招待リンクを開いても友達にならず、使えないリンクと同じ表示になります。

## 8. 保存する期間
- アカウント（メールアドレス・表示名・タイムゾーン・Google の識別子）、友達、設定、くり返し：退会したときに消します。
- ここ暇の枠：始まってから2日で消します（枠は最長1日なので、終わってから1〜2日です）。
- 行きたいと、行きたいを見せない友達：あなたが消したとき、退会したときに消します。置いた回数の記録（置いた回数の上限を数えるため。中身は入りません）は、置いてから2日で消します。
- 行きたいをAIで探した回数の記録（1日に探せる回数を数えるため）：その日から4日目に消します。
- くり返しの、予定で外れた日の記録：その日から3日目に消します。
- 誘い・募集・成立した予定：予定の時間（「この時間なら」で代わりの時間があれば、遅い方）が終わってから30日で消します。
- お知らせの日ごとの数（1日に送る通知の上限を数えるため）：その日から4日目に消します。
- お知らせ：作ってから30日で消します。新しい端末でのログインのお知らせに入る、ブラウザ名と OS 名の要約も同じです。
- 招待リンク：期限から30日で消します。
- ブロック：ブロックをやめたとき、どちらかが退会したときに消します（期限はありません）。
- ログインの記録：使えなくなってから30日で消します。新しい端末でのログインに気づくため、最初のログインの記録だけは退会まで残します。
- プッシュ通知の宛先：ログアウトしたとき、届けられなくなったとき、ログインが切れたとき、退会したときに消します。
- カレンダーの許可：連携を解除したとき、Google 側で許可が取り消されたとき、退会したときに消します。
- カレンダーの連携の記録（連携したことと、その状態）と、「ここ暇」カレンダーの識別子：連携を解除しても残し、退会したときに消します（もう一度連携したときに、同じ「ここ暇」カレンダーを使うため）。
- カレンダーの空き／埋まりの記録：連携を解除したとき、30日アプリを開かなかったとき、退会したときに消します。
- カレンダーの空き／埋まりの一時的な記録：5分で消えます。連携を解除しても、最長5分は残ります。
- リンクのプレビュー：使う誘い・募集がなくなり、取ってから30日を過ぎたら消します。
- リンクのプレビューの画像：使うプレビューがなくなってから1時間で消します。
- アイコンの画像：変えた・外した・退会したときから1時間で消します。すでに表示した端末には、最長2時間残ることがあります。
- 処理の記録：処理してから7日で消します。まだ送り始めていない通知の記録は、作ってから30日で消します。うまく処理できなかった記録は4日で消えます。
- 二重の送信を防ぐための記録：24時間で消します。
- 問い合わせ：運営に届けたら、このサービスのデータベースから内容を消します。うまく届かなかったものは、処理の記録として7日で消えます。運営の連絡用の Slack に届いたものは、対応を終えたら消し、遅くとも Slack に届いてから90日で消えます。
- 通報：問い合わせと同じです。運営に届けたら、このサービスのデータベースから内容を消し、うまく届かなかったものは7日で消えます。Slack に届いたものは、対応を終えたら消し、遅くとも Slack に届いてから90日で消えます。
- ログ：7日で消えます。
- データベースの復元用の記録：消したあとも、最大30日は復元のための記録に残ります。
- 外部の事業者（「5.」）が持つ記録（メールの送信の記録など）は、それぞれの事業者の定めによります。

### 退会したとき
- 退会すると、すぐに名前・メールアドレス・ログイン・友達・ブロック（あなたがした・あなたがされた）・ここ暇・行きたい・設定・あなたあてのお知らせ・プッシュ通知の宛先を消します。取り消しはできません。
- アイコンの画像は、退会してから1時間で消します。
- AIで探した回数の記録は、退会したときにあなたとのつながりを切り、上の期間で消します（サービス全体の1日の回数を数えるため、時刻と結果の種類だけが残ります）。
- 続けて、あなたが誘い・募集に書いたひとこと・エリア・リンクを消し、あなたの Google カレンダーの「ここ暇」カレンダーを消して、Google の許可を取り消します。この処理は退会のあとに自動で行い、うまくいかなかったときは、やり直します。
- これからの成立した予定は、「やっぱり難しい」を押したのと同じになります。返事を待っている誘い・募集も終わります。
- 次のものは、相手のために残り、上の期間で消えます。
  - 相手の履歴（誘い・募集・成立した予定の日時、相手、返事）。相手には「退会したユーザー」と出ます。予定の時間が終わってから30日で消えます。
  - 相手あてのお知らせ（あなたからだったことを含みます）。作ってから30日で消えます。
  - 相手に関わる処理の記録。上の「処理の記録」の期間で消えます。
  - カレンダーの空き／埋まりの一時的な記録。最長5分で消えます。
- まだ運営に届いていない問い合わせと通報は、届けずに消します。退会とほぼ同時（数秒のうち）に届いたものと、退会の前に届いたものは、上の「問い合わせ」「通報」の期間で消えます（運営が気づいたものは、その時点で消します）。あなたについての通報は、通報した人のものなので、あなたが退会しても上の期間で消えるまで残ります。
- 利用者を区別する番号と、退会した時刻だけは残します（相手の履歴を「退会したユーザー」と出すため）。

### 10. リンクのプレビューの画像の削除の求め（手での対応）
- 第5条3の求めは、運営がメールで受け、手で対応する（運営用の機能は作らない。決めたこと13）。手順書は #90 の残り（スコープ外）にあるので、ここには消し方の決まりだけを書く。
- 消すのは、T-08 の画像を消す道（毎分の掃除）を使う。R2 の物と台帳（`link_preview_images`）の行を、手で直接は消さない（T-08「掃除」：画像を消す道は1つだけ）。
  1. 求めのあった画像の `image_id`（画像の URL の `/api/v1/link-previews/images/<image_id>`）から、それを参照する `link_previews` の行を見つける。同じ URL（`url_hash`）の `ok` の行もすべて対象にする（使い回しで、同じ画像を参照しているため）。
  2. その行の `image_id` を、`WHERE id = ? AND status = 'ok' AND image_id = ?` の条件付き UPDATE で `NULL` にする（本番の D1 への手での書き込み。プレビューのタイトルなどは残し、画像だけが出なくなる）。
  3. 参照がなくなった画像は、T-08 の掃除で、R2 の物を消してから台帳の行が消える（台帳の `created_at` から1時間を過ぎていれば、次の毎分の掃除で）。消えたことを、管理画面で確かめる。
- 残るもの（第5条3の「しばらく残る」）：画像の経路は `Cache-Control: public, max-age=86400, immutable`（T-08）なので、すでに表示した端末には最長1日残る。消したあとに画像の URL を開くと404になる。
- 写し直し：T-08 では、`ok` の結果を7日使い回したあと、同じ URL が付けられると取り直し、画像も写し直す（T-08「取得のきっかけ」3）。同じ URL を写し直さないようにするには、T-08 の仕様の変更が要る（例：削除の求めのあった `url_hash` を D1 に記録し、その URL では画像を写さない）。この仕様書では作らず、T-08 への申し送りにする（「実装PRで直すもの」）。それまでは、求めた人に、同じリンクがまた付けられると写し直すことがあると伝え、気づいたら同じ手順で消す。
