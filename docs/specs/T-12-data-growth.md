## 概要
- いまの定期処理は、outbox を1分に100件までしか流せない。カレンダーの確認も15分に200人まで（1時間に800人）しか割り当てられない。利用者が増えると、通知と自動取り消しが遅れる。
- 処理済みの outbox の行と、終わったここ暇の行が消えずに増え続ける。ここ暇を探す SQL は、その人の過去の行まで毎回読む。
- 毎分の掃除の一部は、インデックスがないため表全体を読む。D1 は書き込みを1本で処理するので、ほかの書き込みを待たせる。
- 定期処理の1つが例外を投げると、後の処理（掃除を含む）が走らず、ログも出ない（#86）。掃除を足すので、あわせて直す。
- この仕様書では、上を直す。API・画面・応答の形は変えない。

## データ
- マイグレーション `0011_data_growth.sql` で、インデックスを足す。表と列は変えない。
  - `ics_tokens (expires_at)`：期限切れのトークンの掃除（`DELETE ... WHERE expires_at <= ?`）に使う。
  - `notification_daily_counts (day)`：古い日の数の掃除（`DELETE ... WHERE day < ?`）に使う。主キー `(user_id, day, channel)` は先頭が `user_id` なので、この条件には使えない。
  - `link_previews (status, fetched_at)`・`link_previews (status, claimed_at)`：古い結果の行の掃除に使う。
- outbox の処理済みの行の掃除には、既存の `outbox_unprocessed (processed_at, created_at)` を使う。
- 終わったここ暇の掃除には、既存の `availabilities_starts (starts_at)` を使う（T-03 で掃除のために作ったもの）。
- 足したインデックスのぶん、行を足すときの書き込みが少し増える。どれも書き込みの少ない表なので受け入れる。

## 振る舞い

### 1. outbox を Queues に流す（T-06「outbox を Queues に流す」の変更）
- 1回の Cron の中で、「最大100件を読む → `sendBatch` → 処理済みにする」を繰り返す。
  - 読んだ件数が100件より少なければ、そこで終える（未処理の行がもうない）。
  - 繰り返しは最大10回とする。1分に流せるのは最大1000件（いまの10倍）になる。
  - 実行を始めてから20秒を過ぎたら、次の回に入らずに終える。次の Cron の実行（1分後）と重ならないようにするため。
- 1回分の手順（読む・送る・処理済みにする）と、「送ってから処理済みにする」「途中で止まっても次の実行で送り直す」は変えない。
- 打ち切ったときは、件数だけのログを出す（「5. 定期処理の独立とログ」）。
  - 10回で打ち切った（未処理の行が残っている見込み）：`{ event: "outbox_dispatch_capped", reason: "count", sent }`
    - 10回目でちょうど未処理の行がなくなった場合も出る（11回目の読み取りはしない）。1分に1000件に達したこと自体が見直しの目安なので、そのまま出す。
  - 20秒で打ち切った：`{ event: "outbox_dispatch_capped", reason: "time", sent }`
- 次の実行との重なり：20秒で打ち切った後も掃除が続くので、実行全体は20秒より長くなりうる。次の Cron の実行と重なり、同じ行を2回送ることがある。
  - これは今の「送ってから処理済みにする」でも起きうることで、consumer はどの処理も冪等なので結果は変わらない（T-06「二重に届くことは、consumer の冪等性で受ける」）。
- 同じ Cron の掃除で、`processed_at` が7日より前の行を消す。
  - 1回の実行で消すのは最大1000行（`DELETE FROM outbox WHERE id IN (SELECT id FROM outbox WHERE processed_at < ? LIMIT 1000)`）。
  - 未処理の行（`processed_at IS NULL`）は消さない。流す型がまだない行も残す（ほかのタスクで型を足したときに流すため）。
  - 7日にする理由：退避キューに入ったメッセージを調べるとき、元の行を見られるようにするため。退避キューの既定の保持期間（4日）より長くしておく。`AvailabilityCancelledByCalendar` の payload に入る時刻などの行動の情報は、7日で消える（T-06 決定事項12で先送りした掃除）。
  - ただし、退避キューを読む手段と調べる手順はまだない（#85）。それができるまでは、7日のあいだ行が残るだけで、調べる流れはない。

### 2. カレンダーの確認の割り当て（T-06「定期の確認と自動取り消し」の変更）
- 15分ごとに割り当てる数の上限を、200人から1000人に上げる。1時間に確かめられるのは最大4000人分になる。連携している人が1000人までなら、1人あたりの間隔は15分のまま。
  - 1000人を超えると間隔が延びる（例：2000人なら約30分ごと）。そのときは上限を見直す（T-06 と同じ）。
  - 超えたことに気づけるよう、選んだ数が上限（1000）に達したら、件数だけのログを出す：`{ event: "calendar_sync_assign_full", assigned }`。
  - Google Calendar API の呼び出しは、15分に1000人で1分あたり約67回の freeBusy になる。
- 選ぶ SQL の並び替えを `ORDER BY last_synced_at` だけにする。
  - SQLite は昇順で NULL を先に並べるので、確認したことがない連携が先に選ばれる点は変わらない。
  - これで、インデックス `calendar_connections_sync (status, last_synced_at)` の順に読んで LIMIT で止まれる。いまの `ORDER BY last_synced_at IS NOT NULL, last_synced_at` では、並び替えのために対象の行を全部読む。
- Queue に送るのは、いままでどおり100件ずつの `sendBatch`。確認の権利（lease）と、確認そのものの手順は変えない。

### 3. ここ暇（手動の枠）の検索と掃除（T-03 の変更）
- 手動の枠は長さが最大24時間（T-03「24時間超は400」）。この性質を使って、範囲と重なる枠を探す SQL に開始日時の条件を足す。
  - 範囲 `[from, to)` と1分以上重なる枠は、必ず `from - 24時間 < starts_at < to` を満たす。この条件を、いまの重なりの条件に **足す**（置き換えない）。
  - これで、インデックス `availabilities_user_starts (user_id, starts_at, id)` の範囲だけを読む。結果は変わらない。
  - 対象：自分の一覧（`listMyManual`）、友達の空き（`visibleManual`）、自動取り消しの対象（`myManualWithCreatedAt`）、追加するときの重なりの判定（`insertManualWithinLimits` の `NOT EXISTS`）。
  - 追加するときの「未来の枠が100個まで」の数え方は、`ends_at > now` に `starts_at > now - 24時間` を足す。
  - 24時間は、ここ暇の長さの上限と同じ定数を使う。上限を変えるときは、この条件も一緒に変わる。
- 終わったここ暇の掃除を、毎分の Cron の掃除に足す。
  - `starts_at` が2日より前の行を消す。長さは最大24時間なので、どれも終わってから1日以上たっている。
  - 期間は「1日＋ここ暇の長さの上限」として決める（コードの `AVAILABILITY_RETENTION_MS`）。長さの上限を変えると、この期間も一緒に変わる。
  - 1回の実行で消すのは最大1000行。
  - 終わった枠は一覧・友達の空き・重なりの判定・自動取り消しのどれにも使わない（T-03「過去の枠は表示しない」）。消しても見え方は変わらない。
  - 誘い・募集・成立は、ここ暇の行を参照していない（時刻を自分で持つ）。消しても影響しない。
  - 匿名の集計（NF-08、#46）で、ここ暇の設定数を数える場合は、行が消える前（作ったとき）に数える必要がある。いまは集計の仕組みがないので、#46 に申し送る。

### 4. 毎分の掃除のインデックス
- 「データ」で足したインデックスを使う。掃除の SQL の条件と、1回に扱う数の上限は変えない。
- 台帳から参照されない画像を探す処理（`orphanImages`）は変えない。結果の行から画像を引く条件は `link_previews.image_id` の UNIQUE のインデックスで引ける。画像の台帳の行の数は、結果の行の数を超えない。

### 5. 定期処理の独立とログ（#86）
- `runScheduled` の毎分の処理（outbox を流す、各掃除）と15分ごとの割り当てを、1つずつ独立させる。
  - 各処理を個別に `try` で囲み、1つが例外を投げても、後の処理は走る。
  - `cleanupExpired` の中の掃除（連携の state、.ics のトークン、ログインの記録、セッションと更新用トークン、冪等キー、お知らせ、リンクのプレビュー、この仕様書で足す outbox とここ暇）も、1つずつ独立させる。
- 失敗したら、構造化したログを1行出す：`{ event: "cron_step_failed", step, name }`。
  - `step` は処理の名前。`dispatch_outbox`・`assign_syncs`・`cleanup_oauth_states`・`cleanup_ics_tokens`・`cleanup_login_records`・`cleanup_sessions`・`cleanup_idempotency_keys`・`cleanup_notifications`・`cleanup_link_previews`・`cleanup_outbox`・`cleanup_availabilities`。
  - `name` は例外の名前（`Error.name`）だけ。`Error` でない値が投げられたときは `"unknown"`。メッセージ・スタック・SQL の値・payload は出さない（個人情報やトークンを含みうるため）。
- 例外を握りつぶしたあとも、Cron の実行自体は成功として終える。失敗はログで気づく（ログのアラートは #85）。

### ログの一覧（#85 のアラートの対象の候補）
| event | 出すとき | 項目 |
| --- | --- | --- |
| `outbox_dispatch_capped` | outbox を10回か20秒で打ち切った | `reason`（`count`・`time`）、`sent` |
| `calendar_sync_assign_full` | カレンダーの確認の割り当てが上限で埋まった | `assigned` |
| `cron_step_failed` | 定期処理の1つが例外を投げた | `step`、`name` |

## 認可と秘匿
- 閲覧者IDの使い方：変えない。友達の空き（`visibleManual`）は、いままでどおり `VISIBLE_OWNERS`（両方向の友達と「見せない」の設定）で絞る。足すのは時刻の条件だけ。
- 他人のデータに届かないことの保証：API を追加しないので、既存の「他人のIDでは取得できない」テストがそのまま通ることで確かめる。
- 区別させない応答：変えない。時刻の条件は、結果を変えないもの（「振る舞い」3）だけを足す。
- 消すデータ：outbox の行動の情報（7日）と、終わったここ暇の行が消える。残す期間が短くなる方向の変更。

## スコープ外
- queue の consumer の並列化（いまは1件ずつ順に処理する）、お知らせの配信の D1 往復の削減。
- フロントエンドのページの遅延読み込み（`React.lazy`）と TanStack Query の `staleTime`。
- 回数の上限（Rate Limiting）を付ける経路の追加、リンクのプレビューの DNS の確認と接続先のずれ。
- くり返しの例外（`recurrence_exceptions`）の過去の日付の掃除。表が小さく、ルールを消すと一緒に消えるため。
- 流す型がまだない outbox の未処理の行の扱い。
- `availabilities_starts` 以外の、使われていないインデックスの整理。
- #38 のうち、この仕様書で扱わない掃除：終わった誘い・募集・予定、使い切った `invite_links`、くり返しの例外。保持期間を決めるのは #38 で続ける。
  - 期限切れの `oauth_transactions`・`login_codes`（`deleteExpiredLoginRecords`）と、失効・期限切れから30日を過ぎた `sessions`・`refresh_tokens`（`deleteDeadSessions`。pryusei/kokohima-app#82）は、すでに掃除している。
- ログを集める経路とアラートの設定、退避キューを読む手段（#85）。
