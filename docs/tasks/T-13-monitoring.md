# T-13 監視とアラート（ログの通知・死活監視・退避キューの調べ方）

## 目的
乗っ取りの疑い・通知が届かない・API の障害・定期処理の停止が起きたとき、運営者（開発者本人）が Slack で気づき、決まった手順で調べて直せるようにする。いまはログが Workers Logs に残るだけで、誰にも届かない。

## 関係する要件
- 要求定義書「技術の選定」の監視（Workers Logs＋利用料アラート）
- 要求定義書「AI時代の攻撃を前提にした運用」：検知から遮断を自動化する（異常のアラート）
- 要求定義書「残りの論点」一般公開までに必須：異常検知のアラートの条件と通知先
- NF-02（外部連携は Queues 経由。失敗時は再試行する）、NF-03（Outbox パターン）
- docs/specs/T-12-data-growth.md「ログの一覧」
- issue：pryusei/kokohima-app#85。関連は #42（利用料アラート・WAF）、#41（監査ログ）、#52（本番までに人が行う作業）、#86（Cron の失敗のログ。T-12 で対応）

## スコープ
- やること：
  - アラートにするログの条件・閾値・通知先（Slack）を決める
  - Cloudflare の Monitors（ログの条件）と Workers Issues（想定外の例外）で、Slack に通知する
  - 定期処理が動いた記録と、深い死活確認の API（`GET /api/v1/health/ready`）を足し、外から監視する
  - アラートに足りないログを足し、ログの重さ（warn・error）をそろえる
  - 運用の手順書（`docs/runbooks/monitoring.md`）を足す：通知の設定、退避キューの調べ方とやり直し方、問い合わせの調べ方、ログを見られる人
- やらないこと（スコープ外）：
  - 利用料アラート、WAF、ボット対策（#42）
  - 監査ログ（#41）、匿名の集計（NF-08、#46）
  - 退避キューを自動で読んでやり直す処理、運営用の画面
  - 画面に問い合わせ番号（`requestId`）を出すこと
  - Cloudflare の管理画面と Slack・外の監視サービスの設定そのもの（人が行う。手順書に書く）
  - `wrangler deploy`・`terraform apply`（人が行う）

## 受け入れ条件
- [x] 定期処理が動くたびに、動いた時刻が記録される。処理の1つが失敗しても記録される
- [x] `GET /api/v1/health/ready` は、定期処理が止まっている・outbox が溜まっている・D1 が読めないときに 503 を返し、それ以外は 200 を返す
- [x] 503 の応答から、どの条件で落ちたか・利用者や件数の情報が分からない（理由はログにだけ出る）
- [x] 同じ1件の失敗が、Monitors と Workers Issues の両方から通知されない（`event` で数えるログは warn 以下、想定外の例外は error で出る）
- [x] サービス全体の1日のメール数の上限に達したとき、種類だけのログが出る
- [x] 本番の wrangler の設定で Workers Issues が有効になっている
- [x] 手順書に、アラートの一覧（条件・閾値・通知先）、Slack と外の監視の設定、退避キューの調べ方とやり直し方、問い合わせの調べ方、ログを見られる人の範囲が書いてある
- [x] ログと通知に、個人情報・トークン・予定の中身が出ない
- [x] 他人のIDでは取得・更新できないテストがある（追加する API は利用者のデータを返さないことを確かめる）
- [x] 単体テストが追加され、通る
- [x] 仕様書でE2Eの対象にした流れのE2Eテストが通る（対象の流れはなし。既存のE2Eが通る）
- [x] 仕様書とコードに齟齬がない（要求定義書の「監視」と「異常検知のアラートの条件と通知先」を実装PRで書き換える）
- [x] typecheck・lint・関係するテストが通る
