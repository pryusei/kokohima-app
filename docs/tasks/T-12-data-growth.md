# T-12 データの増加への備え（outbox・カレンダーの確認・ここ暇の検索・毎分の掃除）

## 目的
利用者とデータが増えても、通知とカレンダーの自動取り消しが遅れず、毎分の定期処理が D1 を無駄に読まないようにする。T-03・T-06 で先送りした掃除と、上限の見直しをまとめて行う。

## 関係する要件
- F-06：自動取り消し（確認の間隔が延びると、取り消しが遅れ、友達に「暇」と見え続ける）
- NF-02：外部連携は Queues 経由の非同期処理
- NF-03：Outbox パターン
- NF-09：有料プランの CPU 時間の上限を踏まえる
- docs/specs/T-03-availability.md「過去の枠の掃除（Cron）」（別タスクとして先送り）
- docs/specs/T-06-calendar.md「人数が増えたら上限を見直す」「処理済みの行の掃除（別タスクの Cron の掃除）」
- issue：#38 の一部、#86。ログは #85 のアラートに引き継ぐ

## スコープ
- やること：
  - outbox を Queues に流す量の上限を上げ、処理済みの行を消す
  - カレンダーの確認の割り当ての上限を上げ、選ぶ SQL をインデックスの順で読めるようにする
  - ここ暇（手動の枠）を探す SQL に開始日時の範囲の条件を足し、終わった枠を消す
  - 毎分の掃除が使うインデックスを足す（`ics_tokens`・`notification_daily_counts`・`link_previews`）
  - 定期処理の各処理を独立させ、失敗と上限での打ち切りをログに出す（pryusei/kokohima-app#86）
- やらないこと（スコープ外）：
  - queue の consumer の並列化、お知らせの配信の D1 往復の削減
  - フロントエンド（`React.lazy`・`staleTime`。T-49 で扱った）
  - 回数の上限（Rate Limiting）の付け足し、リンクのプレビューの DNS の検査
  - くり返しの例外の日付の掃除

## 受け入れ条件
- [x] outbox に未処理の行が多いとき、1回の Cron で100件を超えて流れる（1分に最大1000件）
- [x] 処理済みになって7日を過ぎた outbox の行が消える。未処理の行は消えない
- [x] 15分ごとの割り当てで、最大1000人分の確認が Queue に送られる。確認したことがない連携が先に選ばれる
- [x] 終わってから1日以上たった手動の枠が消え、一覧・友達の空き・重なりの判定・自動取り消しの結果は変わらない
- [x] 掃除と割り当ての SQL が、表全体を読まずにインデックスを使う（`EXPLAIN QUERY PLAN` で確かめる）
- [x] 定期処理の1つが例外を投げても残りの処理が走り、`cron_step_failed` のログが出る
- [x] outbox を上限で打ち切ったとき・確認の割り当てが上限で埋まったときに、件数だけのログが出る
- [x] 他人のIDでは取得・更新できないテストがある（API の追加はないので、既存のテストが通ること）
- [x] 単体テストが追加され、通る
- [x] 仕様書でE2Eの対象にした流れのE2Eテストが通る（対象の流れはなし。既存のE2Eが通る）
- [x] 仕様書とコードに齟齬がない（T-03・T-06 の仕様書の該当箇所を実装PRで書き換える）
- [x] typecheck・lint・関係するテストが通る
