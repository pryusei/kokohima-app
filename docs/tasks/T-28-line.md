# T-28 LINE連携（招待リンクをLINEで送る・お知らせをLINEで受け取る）

## 目的
友達とのやりとりはLINEが入口になっている（要求定義書「既存の手段」「LINEで足りると言われる」）。LINEと張り合わず、LINEを入口に使う。
- 招待リンクを、LINEのトークにそのまま送れるようにする。開いた友達が、Googleのログインを断られるLINEのアプリ内ブラウザではなく、Safari・Chromeで開くようにする。
- お知らせの合図を、LINEの公式アカウントから受け取れるようにする。iOSでホーム画面に追加していない人にも、メールより気づきやすい形で届ける。中身（相手の名前・誘いの内容）はLINEに渡さない（T-07 と同じ）。

## 関係する要件
- F-08：友達追加（招待リンクを都度発行し、LINEなどで送る）
- F-16：通知（Webプッシュとメールに、LINEを足す）
- NF-02・NF-07：外部連携は Queues 経由、1日の上限と停止設定
- 要求定義書「リスクと対策」：友達が使わない（LINEに貼れる招待リンク）、iOSのWebプッシュが届かない、LINEで足りると言われる
- セキュリティ設計：外に出ている窓口の一覧（Webhookの受け口が増える）、ログに個人情報を出さない

## スコープ
- やること：
  - 招待リンクの発行のシートに「LINEで送る」を足す（`line.me` の共有のURLを開くだけ。LINEのAPIは呼ばない）
  - LINEで開いたとき外のブラウザで開くよう、送るURLに `openExternalBrowser=1` を付ける
  - 通知の設定に「LINEで受け取る」を足す：LINEログイン（OAuth）でLINEの利用者IDを受け取り、公式アカウントの友だち追加をすすめる
  - お知らせの届け方に `line` を足す：連携していて友だち追加済みならLINEに中身のない合図を送り、プッシュ・メールは送らない。届かなければ今の届け方に戻す
  - 未読の合図がすでにLINEに届いていれば、次の合図を送らない（まとめる）。1人1日の上限と、サービス全体の1か月の上限
  - Webhookの受け口（友だち追加・ブロックだけを扱う。署名を確かめる）
  - 連携の解除、退会での削除
  - プライバシー ポリシーの本文（実装PRで直す。T-19 の決まりで、効力の前に知らせる）
- やらないこと（スコープ外）：
  - LINEでのログイン（F-01 は変えない）
  - 中身のあるメッセージ（相手の名前・誘いの内容・ボタンつきのメッセージ）、LINEのトークからの返答
  - LINEのグループへの募集の投稿、LIFF、リッチメニュー
  - 誘い・募集・予定のURLをLINEで送るボタン（宛先はアプリの友達で、お知らせで届くため）

## 受け入れ条件
- [ ] 招待リンクを作ったシートに「LINEで送る」があり、押すとLINEの送り先を選ぶ画面が開き、本文に招待リンクが入っている
- [ ] LINEのトークで招待リンクを開くと、Safari・Chromeなど外のブラウザで開く（実機で確かめる）
- [ ] 通知の設定から「LINEで受け取る」を押し、LINEで許可して公式アカウントを友だち追加すると、設定に「LINEで受け取っています」と出る
- [ ] 連携していて友だち追加済みの人には、お知らせの合図がLINEに届き、プッシュ・メールは届かない。合図に相手の名前・誘いの内容が入らない
- [ ] 未読の合図がLINEに届いている間は、次のお知らせでLINEを送らない（お知らせ一覧には出る）
- [ ] ブロック・友だち解除・連携の解除・上限・LINE側の失敗のときは、今のプッシュ・メールで届く
- [ ] 新端末のログインは、今のとおりメールで届く
- [ ] 他人のIDでは取得・更新できないテストがある。他人のLINE連携を作れない・消せない
- [ ] Webhookは署名が合わなければ何もしない。友だち追加・ブロック以外のイベントを保存もログもしない
- [ ] 単体テストが追加され、通る
- [ ] 仕様書でE2Eの対象にした流れのE2Eテストが通る
- [ ] 仕様書とコードに齟齬がない（仕様の変更は仕様書に反映済み）
- [ ] typecheck・lint・関係するテストが通る
