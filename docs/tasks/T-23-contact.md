# T-23 問い合わせのフォーム

## 目的
ログインしている利用者が、設定から運営に不具合・ご意見・個人情報の開示や削除の請求を送れるようにする。送った内容は、運営者だけが入る Slack の非公開のチャンネルに届き、運営者は登録のメールアドレスに返事をする。

## 関係する要件
- 要求定義書「機能要件」：F-22 問い合わせ（実装PRで足す）
- 要求定義書「AI時代の攻撃を前提にした運用」（保存するデータを減らす）：内容は届けるまでの間だけ D1 に持ち、届けたら消す
- T-19（プライバシー ポリシーの「3.」8 問い合わせに答える、「12.」開示・削除の求め）。ログインできない人は今までどおり `ops@kokohima.app`
- 関連：T-10（冪等キー・回数の上限）、T-13（監視・退避キュー）、T-16（退会）、T-17（保持期間）、T-11・T-20（画面）

## スコープ
- やること：
  - 受け口 `POST /api/v1/contact-messages`（ログインした人だけ。outbox に1行書くだけ。1人24時間に5件まで）
  - consumer で Slack の Incoming Webhook に送る（利用者の文を `plain_text` に入れ、`&`・`<`・`>` をエスケープし、メンション・リンクを起こさせない）。返信先のメールアドレスは送る時に読む
  - 届けたら outbox の内容を消す。退会した人の問い合わせは届けない
  - 設定のトップの「このアプリについて」に「問い合わせ」を足し、`/settings/contact` の画面（種類のチップ、内容と文字数、静かな成功と失敗）を作る。部品 `textareaClass`・`CharCount` を `apps/web/src/ui/form.tsx` に足す
  - 秘密情報 `CONTACT_SLACK_WEBHOOK_URL`（`wrangler secret` だけ）と、E2E の偽の Slack
  - プライバシー ポリシー（集める情報・目的・委託先 Slack・外国にある事業者への提供・保存期間・開示の求め）、手順書（専用のチャンネル、ログの本文を Slack に流さない決まりの例外、問い合わせの受け方）、デザインの資料（画面一覧・プロンプト・T-11）を直す
- やらないこと（スコープ外）：
  - ログインしていない人のフォーム、自動の返信メール、送った問い合わせの一覧、画面からの返事
  - ファイルの添付、D1 への保存・集計、Slack 以外の届け先
  - 全体の回数の上限、今のひとことの入力欄の見直し

## 受け入れ条件
- [ ] ログインした人が、設定 → 「問い合わせ」で種類を選んで内容を書いて送ると、「送りました」が静かに出て、`#kokohima-contact` に1通届く
- [ ] 届いた文に、種類・内容・返信先（送り主の登録のメールアドレス）・利用者 ID・受け付けた時刻・問い合わせ番号が入り、内容の `<!channel>`・`<@...>`・`<URL|文字>` などがメンション・リンクにならず、リンクの展開も起きない
- [ ] 送り主はいつもアクセストークンの本人で、本文で偽れない。ログインしていない・退会した人は送れない
- [ ] 1人24時間に6件目は送れず、静かな文言が出る。内容は1〜2000文字、本文は16KiB まで
- [ ] 同じ `Idempotency-Key` の再送で、2通届かない
- [ ] outbox の payload にメールアドレスが入らず、届けたら種類と内容が消える。届かなければ再試行され、最後は退避キューに入って `job_dead_lettered` で気づける
- [ ] ログ・例外のメッセージに、内容・メールアドレス・利用者 ID・webhook の URL が出ない
- [ ] 送れなかったとき、赤やエラー色を使わずに文言が出て、入力が残る。オフラインでは押せない
- [ ] プライバシー ポリシー・手順書・T-10・T-11・T-16・T-17・デザインの資料が、仕様書の「実装PRで直すもの」のとおり直っている
- [ ] 他人のIDでは取得・更新できないテストがある（本文に別の利用者の ID を入れても、送り主は本人のまま）
- [ ] 単体テストが追加され、通る
- [ ] 仕様書でE2Eの対象にした流れのE2Eテストが通る
- [ ] 仕様書とコードに齟齬がない（仕様の変更は仕様書に反映済み）
- [ ] typecheck・lint・関係するテストが通る
