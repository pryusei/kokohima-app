# T-17 仕様書：古いデータの掃除と保持期間

- 状態：下書き
- タスク票：docs/tasks/T-17-retention.md
- 関係する要件：要求定義書「AI時代の攻撃を前提にした運用」（保存するデータを減らす）、NF-08。issue pryusei/kokohima-app#38 の残り

## 概要
終わった誘い・募集・成立した予定は、今は無期限に残っている（相手・時刻・エリア・ひとこと・リンク）。これを、予定の時間の終わりから30日で、毎分の掃除で消す。お知らせも30日にそろえる。期限の過ぎた招待リンク、過去のくり返しの例外、友達でなくなった相手との公開設定、流れないまま残る通知の記録も消す。また、30日アプリを開いていない人（休眠中の人）の連携では、カレンダーの定期の確認を止め、埋まりの記録を消す。表ごとの保持期間は1つの表にまとめる。

## 決めたこと（利用者の回答）
1. 終わった誘い・募集・成立した予定は、終わってから30日で消す。
2. お知らせも、すべて30日で消す（今は90日。T-07 を直す）。
3. 休眠中の人＝使える更新用トークンがない人（アプリを30日開かないと、更新用トークンが切れてログインし直しが要る。T-01）。休眠中の人の、カレンダーの定期の確認は止める。
4. 休眠になったら、埋まりの記録を消す。Google の許可（更新用トークン）は残し、連携は続く。ログインし直したら、新しく連携したときと同じく「記録だけ」から始める（まとめての取り消しは起きない）。
5. 友達を解除したら、両方向の公開設定を消す。友達に戻ったら初期値（見せる）から。
6. 成立数の集計（NF-08）のための記録は、今は残さない。過去の成立を後から数えられなくなることを受け入れる（#46 で集計を作るときに決める）。

## API
変更なし。ただし、次の応答が変わる。
- 期限から30日を過ぎた自分の招待リンクの無効化（`POST /invite-links/{id}/revoke`）は、行が消えるので204でなく404になる（T-02 の「期限切れでも204」を直す）。
- 消えた誘い・募集・予定は、ほかの見つからないものと同じ404。

## データ
マイグレーション（その時点の次の空いている番号）：
- 列：`calendar_connections.dormant_since INTEGER`（NULL なら休眠でない）。
- インデックス：
  - `direct_invites (ends_at)`、`broadcasts (ends_at)`、`invite_links (expires_at)`、`recurrence_exceptions (local_date)`（掃除で表全体を読まない）
  - `ics_tokens (meetup_id)`（予定を消すときの CASCADE の子の検索。ほかの子の列は UNIQUE か主キーで、すでにインデックスがある）
  - `calendar_connections (status, dormant_since, last_synced_at)`（定期の確認の割り当て。休眠中の行を範囲の外にする。今の `(status, last_synced_at)` を置き換える）
- 今ある、友達でない相手との公開設定の行を消す（`DELETE FROM sharing_policies WHERE NOT EXISTS (両方向の friendships)`。1回だけ）。

### 2. 終わった誘い・募集・予定
- 毎分の掃除で、次の行を消す。状態では絞らない（誘いの期限は開始まで。T-04。時間の終わりを過ぎていれば、どの状態でも終わっている）。
  - 誘い：`ends_at < ?cutoff AND (counter_ends_at IS NULL OR counter_ends_at < ?cutoff)`。`?cutoff` は今から30日前。代わりの時間で成立した予定は代わりの時間で作られるので、その終わりまで待つ。代わりの時間が元の時間よりずっと後の行は、毎回読んで外すことになるが、数は少ない。
  - 募集：`ends_at < ?cutoff`。
- 予定（`meetups`）・参加者（`meetup_participants`）・宛先（`broadcast_recipients`）・.ics の鍵（`ics_tokens`）・リンクの参照（`link_preview_refs`）は、外部キーの CASCADE で一緒に消える。予定は誘い・募集と同じ時間なので、予定だけ先に消えることも、予定だけ残ることもない。参照がなくなったリンクのプレビューは、T-08 の掃除で消える。
- 両方の参加者の履歴から同時に消える。お知らせも30日で消えるので（「3.」）、片方の人にだけ相手の記録が長く残ることはない。
- 1回に消す数：誘いは1000行（`CLEANUP_BATCH`）、募集は100行（宛先が最大100人いて、CASCADE で消える行が多いため）。`DELETE ... WHERE id IN (SELECT id ... ORDER BY ends_at LIMIT ?)`。
- 自分の Google の「ここ暇」カレンダーに書いた、過去の予定は消さない（予定の書き込みは、終わった予定を消さない。T-06）。

### 3. お知らせ
- 作ってから30日（`inserted_at`）を過ぎたお知らせを消す（今の90日の掃除の期間を変える。インデックス `notifications_inserted` を使う）。
- 30日より前の誘い・予定を指すお知らせはなくなる（お知らせを開いて「見つかりませんでした」になるのは、30日の境目の前後だけ）。

### 4. 流れないままの通知の記録
- `NOTIFICATION_START_AT` が未設定の間（T-07。今の staging・prod）、通知だけの型（`NOTIFICATION_ONLY_TYPES`）の outbox の行は、流れず処理済みにもならない。T-12 の掃除は処理済みの行しか消さないので、誰が誰の誘いを断ったかなどが残り続ける。
- 未設定の間は、通知だけの型で、未処理で、作ってから30日を過ぎた行を消す（1回に1000行。インデックス `outbox_unprocessed (processed_at, created_at)`）。設定したあとは、その時刻より前の行は流さずに処理済みにする今の動き（T-07）のとおり。

### 5. 招待リンク
- 期限 `expires_at` が今から30日より前の行を消す（使い切ったもの・無効化したものも、期限で消える。期限は最長7日。T-02）。1回に1000行。

### 6. くり返しの例外
- `local_date` が、UTC の今日の2日前の日付より前の行を消す（日付の当日・翌日・翌々日は残る）。タイムゾーンの差は最大1日なので、どのタイムゾーンでも過去の日付になっている。表示は、終わっていない枠と今日以降の例外しか使わないので変わらない。1回に1000行。
- ルールを消すと、例外は CASCADE で消える（今のまま）。

### 7. 公開設定
- 友達を解除する batch（T-02）で、両方向の `sharing_policies` も消す。退会では今も消している（T-16）。
- 友達に戻ったら、行がないので初期値（見せる）。前の「見せない」は引き継がない。
- 自動の「今回は難しい」の判定（`viewersWhoCanSee`。T-06 決定事項15）は、友達関係の作成時刻でも見ているので、解除して戻った相手は、戻った時刻より前の取り消しでは見られない側のまま（変わらない）。

### 8. 休眠中の連携
- **休眠にする**：毎分の掃除で、次の条件の連携を休眠にする（1回に100行）。
  - `status = 'active' AND dormant_since IS NULL`
  - その利用者に、使える更新用トークンがない：`NOT EXISTS (SELECT 1 FROM sessions s JOIN refresh_tokens rt ON rt.session_id = s.id WHERE s.user_id = c.user_id AND s.revoked_at IS NULL AND s.expires_at > ?now AND rt.used_at IS NULL AND rt.expires_at > ?now)`
  - 書く値：`dormant_since = ?now`、埋まりの記録（`busy_snapshot`・`snapshot_from`・`snapshot_to`・`last_synced_at`）を NULL、`large_change_held = 0`。更新用トークンと `calendar_id` は残す。
- **休眠中**：
  - 定期の確認の割り当て（`connectionsDueForSync`）は `dormant_since IS NULL` の行だけ（インデックスの範囲で外れる）。Google の埋まりの取得、ここ暇の自動の取り消し（T-06）、そこからの自動の「今回は難しい」が止まる。
  - 止まらないもの：成立した予定の書き込み（`activeConnectionsOf`。友達が休眠中の人と予定を作れば、その人のカレンダーに書く）。そのとき Google の更新用トークンが切れていれば、今の扱い（`needs_reauth`。T-06）になる。
  - 受け入れること：休眠中は、カレンダーで埋まった時間のここ暇（くり返しは毎週展開されるので、とくに）が、友達に空いているように見えることがある。誘いは届くが、本人はアプリを開いていない。
- **戻す**：ログインでセッションを作ったとき（T-01 の `createSession`。アプリを開いて更新用トークンで更新したときは、トークンが使えるので休眠になっていない）に、その利用者の連携の `dormant_since` を NULL にする（identity から calendar の application の関数を呼ぶ）。埋まりの記録がないので、次の確認は「記録だけ」から始まる（T-06 の確認の手順3）。休眠の間に入った予定で、ここ暇がまとめて取り消されることはない。
- 退会した人の連携は、今のとおり扱わない（T-16）。

### 9. 掃除の書き方とログ
- `apps/api/src/jobs/dispatch.ts` の `cleanupExpired` に足す。ほかの掃除と同じく `runStep` で1つずつ独立させる（T-12 データの増加）。step の名前：`cleanup_invitations`・`cleanup_broadcasts`・`cleanup_invite_links`・`cleanup_recurrence_exceptions`・`cleanup_stale_notification_outbox`・`mark_dormant_connections`。お知らせは今の `cleanup_notifications` の期間を変えるだけ。
- SQL は各コンテキストの infra に置く（invitation：誘い・募集、social：招待リンク、availability：例外・公開設定、notification：お知らせ、calendar：休眠、jobs：outbox）。
- 上限いっぱいまで消した（残っている見込み）ときは、`{ event: "cleanup_capped", step, deleted }` を出す（件数だけ。ID は出さない。T-13 のログの一覧に足す）。

## 認可と秘匿
- 閲覧者IDの使い方：API がないので、閲覧者はいない。掃除はすべての利用者の行を、時刻と状態だけで選ぶ。休眠を戻すのは、ログインした本人の連携だけ。
- 他人のデータに届かないことの保証：消すのは時刻の条件に当たる行だけ。両方の参加者の履歴とお知らせが同じ30日で消えるので、片方だけに長く残って相手を推測させることはない。
- 区別させない応答：変わらない（消えた誘い・予定は、ほかの見つからないものと同じ404）。
- ログ：件数と step の名前だけ。
